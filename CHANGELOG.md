| 2026-04-16 | Context fast path — account for output tokens in `shouldSkipCounting`. The prior estimator summed only `lastInputTokens + newContentEstimate`, but the starting input for turn `N+1` is `turn N input + turn N output + new user content` (the assistant's reply is persisted into history). One response worth of tokens was unaccounted for — enough to slip past the 50% threshold and skip counting when the conversation was actually close to the limit. Fix: new `messages.output_tokens` column (`NOT NULL`, no default), backfilled with `-1` ("unknown, force count") for pre-migration rows via `migrations/0008_needy_ultimo.sql` (add nullable → UPDATE → SET NOT NULL pattern, safe on tables with existing data). `insertMessages` now requires `lastMessageOutputTokens` — written to the final row only; intermediate tool turns and the singular `insertMessage` user-row path store the `-1` sentinel (harmless — the fast path only reads the last assistant row). `getLastInputTokens` renamed to `getLastTokens`, returns `{ inputTokens, outputTokens } \| null`. Estimator: `lastIn + lastOut + ceil(newChars/4) < budget * 0.5`, with any negative/null on either field forcing a real count. 0.5 threshold unchanged — prior ambiguity was accidental lenience, not a design margin; adding the output term tightens the estimate correctly. New tests cover: both counts round-trip through the store, fast path returns false when `N+M+newChars/4` clears 50% but `N+newChars/4` alone wouldn't, boundary at exactly `budget * 0.5` (strict `<`), sentinel `-1` on either value forces count. |
