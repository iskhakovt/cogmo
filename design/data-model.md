# Data Model

All application state in PostgreSQL. Hindsight manages its own tables for memory/vector storage. These are the application tables.

## Source of Truth

Drizzle ORM schema in `src/db/schema.ts`. Migrations generated by `drizzle-kit generate`, applied by `drizzle-kit migrate`. Output in `migrations/`.

## Hindsight Tables (Managed Externally) `[confirmed]`

Hindsight creates and manages its own tables in the same database. Do not modify directly — interact via the Hindsight TS SDK (`retain`, `recall`, `reflect`). Memory metadata (agent_id, source, confidence, mention_count, last_mentioned_at) stored as Hindsight metadata fields.

## Schema Design Decisions `[confirmed]`

### Why Drizzle over raw SQL

- TypeScript schema is the source of truth — types flow into application code automatically
- `drizzle-kit generate` produces reviewable SQL migration files
- Tiny runtime (5KB), SQL-like query API, no magic

### Why `messages` not `session_history`

Industry standard naming. Every reference implementation (Letta, LangGraph, Tiger Data) uses "messages". Avoids confusion with "session" vs "conversation" terminology.

### Why split token columns

`input_tokens` + `output_tokens` instead of single `token_count`. Enables accurate cost attribution — input and output tokens have different pricing. Also useful for context window budgeting (input tokens = how much context was consumed).

### Why `metadata JSONB` on conversations and messages

Universal extensibility pattern across all production agent systems (Letta, LangGraph, OpenAI Assistants). Avoids schema churn for per-message annotations, debug info, or channel-specific data.

### Why no TimescaleDB / hypertables

Researched for message partitioning. Benefits emerge at 10M+ rows with sustained high insert rates. Personal assistant at ~100s messages/day won't reach that for years. Regular PostgreSQL with `(conversation_id, created_at)` index is sufficient. Revisit if message volume grows significantly — migration to hypertables is additive.

### Why no separate tool_calls table

Anthropic SDK returns tool_use and tool_result as content blocks within messages. Storing as JSONB in `messages.content` preserves the native format and avoids a join for context assembly. If we need to query tool usage patterns later, we can extract from JSONB or add a materialized view.

### Why lean (3 tables, not 7)

Drizzle migrations make adding tables trivial. Ship what Phase 1 needs, add the rest when their phase starts. Avoids maintaining unused schema through early iterations.
