# Data Model

All application state in PostgreSQL 18+ (UUID v7 native). Hindsight manages its own tables for memory/vector storage. These are the application tables.

## Source of Truth

Drizzle ORM schema in `src/db/schema.ts`. Migrations generated by `drizzle-kit generate`, applied by `drizzle-kit migrate`. Output in `migrations/`.

UUID v7 for all primary keys (DB-generated via `uuidv7()`). Fallback SQL function in `scripts/init-db.sql` for PostgreSQL 14-17.

All DB operations use transactions.

## Domain Model `[proposed]`

Note: this schema is a design sketch from domain scoping. Validate against real usage before treating as final — column types, relationships, and even table boundaries may change.

```
User
  └── Profile (per-user agent configuration: prompt, model, tools)

Conversation (dialogue with shared LLM context, no lifecycle — just goes idle)
  ├── belongs to User
  ├── uses a Profile
  └── has many Messages

Chat (persistent channel endpoint — Telegram DM, CLI terminal, Slack thread)
  ├── belongs to User
  ├── linked to one active Conversation (nullable)
  └── has an address (polymorphic jsonb: { channel: "telegram", chatId: 123 })

InboundMessage (raw message persisted immediately on arrival — durability buffer)
  ├── belongs to Chat
  ├── linked to a Message when processed (nullable)
  └── has a status lifecycle: pending → processing → processed

Message (a turn in a conversation — what was said, may be a batch of inbound messages)
  └── belongs to Conversation

Delivery (how a message was transported — inbound or outbound through a chat)
  ├── belongs to Message
  └── belongs to Chat

SteeringRule (dynamic behavioral rule injected into system prompt)
  └── optionally scoped to a Profile (null = global)
```

Key separations:
- **Buffer vs content** — InboundMessages are durability insurance. Messages are the dialogue.
- **Content vs transport** — Messages are what was said. Deliveries are how it moved.
- **Dialogue vs endpoint** — Conversations are the thread. Chats are where you reach the user.
- **Configuration vs execution** — Profiles define the agent setup. Conversations use a profile.

## Message Flow

```
Channel receives message
  → persist InboundMessage immediately (status: pending)
  → emit event (pointer to inbound message, not payload)
  → debounce + batch logic (configurable per profile)
  → orchestrator picks up batch of pending InboundMessages
  → creates one Message (conversation turn) from the batch
  → stamps InboundMessages as processed (sets messageId FK)
  → runs agent loop → creates assistant Message
  → response router creates Deliveries to target chats
```

### Debounce Configuration

```typescript
interface DebounceConfig {
  /** Time since last message before firing. Resets on each new message. */
  idleTimeoutMs?: number;
  /** Time since first unbatched message. Never resets. Hard deadline. */
  maxWaitMs?: number;
  /** What to do with messages buffered while the orchestrator was busy. */
  resumePolicy: ResumePolicy;
}

/**
 * Controls what happens to messages that were buffered while the orchestrator
 * was busy processing a previous turn. When the orchestrator finishes and
 * becomes idle, this policy determines how buffered messages are handled.
 */
type ResumePolicy =
  | "debounce"     // re-apply debounce rules (user might still be typing)
  | "flush"        // process buffered messages immediately
  | "await_input"  // hold until user sends another message or confirms
```

| idleTimeoutMs | maxWaitMs | Behavior |
|---|---|---|
| set | set | Fire on whichever comes first. The standard. |
| set | unset | Pure debounce. Could wait indefinitely. |
| unset | set | Pure throttle. Fire every N ms. |
| unset | unset | No batching. Process each message as it arrives. |

### Concurrency

One message batch at a time per chat (serialized). Inngest `concurrency: { limit: 1, key: chatId }`. Second batch waits until first completes.

## Schema Design Decisions `[proposed]`

These decisions reflect the domain scoping exercise. They guide the schema direction but may be revised during implementation.

### Why UUID v7 for all PKs

Time-ordered (good B-tree insert performance), globally unique (no sequence coordination), DB-generated (clients don't provide IDs — prevents wrong UUID versions, timestamp manipulation, and discovery attacks).

### Why inbound_messages separate from messages

Inbound messages are persisted immediately for durability — we can't lose a webhook payload. Messages are conversation turns created by the orchestrator, possibly batching multiple inbound messages into one turn. Different lifecycles, different consumers.

### Why separate messages and deliveries

A message is content ("what was said"). A delivery is transport ("how it moved"). One assistant message can be delivered to multiple chats (reply-to-all routing). Mixing them would mean duplicating content per destination or cramming transport metadata into content rows.

### Why conversations have no `ended_at`

Conversations don't end — they go idle. There's no lifecycle to manage. `/new` creates a new conversation and relinks the chat. The old conversation stays in the DB. Reflection runs on any conversation that meets the threshold (time since last reflection + message count), active or idle.

### Why profiles exist

Different use cases need different agent configurations: a coding assistant uses different prompts, tools, and possibly models than a casual chat buddy. Profiles are per-user so each user can customize their own variants.

### Why steering rules are separate from prompts

They evolve at different rates. Base prompt changes slowly (optimized globally). Steering rules change fast (added/removed per correction, per context). Rules can be toggled, prioritized, scoped to profiles. A prompt template can't do that.

### Why serialized per chat

Agents are not thread-safe per conversation (confirmed by Letta docs). Concurrent processing of messages for the same chat causes race conditions in context assembly. Serialize with `concurrency: { limit: 1, key: chatId }`.

### Why debounce with resume policy

Users send multiple messages rapidly. Batching them into one LLM call is cheaper, gives better context, and produces more natural responses. The resume policy handles the edge case of messages buffered while the orchestrator was busy — configurable per profile because coding workflows (await_input) differ from casual chat (debounce).
