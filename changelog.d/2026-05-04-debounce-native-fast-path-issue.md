Debounce native-fast-path (issue #121). The cancel-based `debounce-idle` / `debounce-maxwait` state machine had a documented race — Inngest registers `cancelOn` listeners after the function starts, so two `debounce/idle` events arriving milliseconds apart both completed and `handle-message` ran 4× for one user turn (Telegram split a long message ~7ms apart, repro). New `createDebounceFunctions` picks one of two paths at construction time: when `idleTimeoutMs >= 1000` and `maxWaitMs` is `0` or `>= 1000` (the production default — 3s/30s), the router carries Inngest's native `debounce: { period, timeout, key: "event.data.conversationId" }` config and dedupes at the queue layer (no cancel-listener race). Sub-second / `idle=0` (no-debounce) / maxwait-only configs fall back to the legacy state machine unchanged. The handle-message staleness guard stays as defence-in-depth (still load-bearing in the legacy path; defends queue-drain after long outages in both). Observability: legacy path records `debounceWaitMs` with `kind: "idle"\|"maxwait"` (exact sleep), native path records `kind: "native"` approximated as `Date.now() - event.ts` (last-event-to-fire). Design doc rewritten with both paths, the race description, observability notes, and a future "collapse to native-only" migration note.
