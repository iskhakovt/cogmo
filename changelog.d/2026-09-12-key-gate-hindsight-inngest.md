**Hindsight and Inngest are key-gated, and boot refuses a server that isn't.** Anything that can reach an unkeyed Hindsight reads and writes every memory bank; anything that can reach an unkeyed Inngest posts `adapter/direct/inbound` (a user turn) or `coding/task/plan-approved` (a plan approval). Both now require credentials, and `cogmo serve` verifies the server enforces them.

- **Hindsight:** `HINDSIGHT_API_KEY` is a **required** env var (also `HINDSIGHT_API_KEY_FILE`). Both Hindsight clients — the class wrapper and the raw sdk client used for recall and reflect — send it as a bearer token, built in `memory/hindsight-clients.ts`. The server runs `ApiKeyTenantExtension` with the same value in `HINDSIGHT_API_TENANT_API_KEY`. Raw sdk failures report the underlying error message and its network cause (`describeError`, which appends undici's `cause` and describes an empty-message `AggregateError` by its inner error or code) rather than `{}` or a bare `fetch failed`.
- **Inngest:** `INNGEST_EVENT_KEY` and `INNGEST_SIGNING_KEY` are required unless `INNGEST_DEV` is set, both accept `_FILE`, and the client hands them to the SDK explicitly.
- **Service URLs:** `HINDSIGHT_URL` and `INNGEST_BASE_URL` are validated by `ServiceUrlSchema`, which rejects `user:password@` for every entrypoint without echoing the value.
- **Auth boot checks:** `checkHindsightAuth` and `checkInngestAuth` fail at once when the server answers an unauthenticated request with a 2xx, or rejects Cogmo's key. The probes leave no trace: Hindsight gets a bank list, Inngest gets `GET /v1/events` plus an empty event batch. Base-URL path prefixes and query strings are kept.
- **Where the probes run:** `checkS3Bucket`, both auth checks and `checkHindsightVersion` run concurrently from `verifyDependencies` in `bootstrap`, so `cogmo serve` and the integration harness probe them. `verifyHindsight` (auth + version, concurrently through `runHindsightChecks`, with an auth failure reported ahead of a version failure) also runs for `migrate-memories` and `backfill`, which clear and rewrite banks, after their arguments and target bank are validated. Other one-shot admin CLIs neither wait on dependencies they don't touch nor need Inngest keys. `checkUuidv7` and the pure Hindsight client-version check stay in `bootstrapCore`, which parses the compat range once.
- **Boot probes fail closed.**
  - **Fail at once:** a deterministic verdict — rejected credentials, an unkeyed server, a version out of range, a missing bucket, a bucket in another region (an S3 301, or a 400 whose `x-amz-bucket-region` differs from `S3_REGION`, named in the error), a half-set S3 key pair (`checkS3KeyPair`), a service URL with embedded credentials. S3 errors are classified by HTTP status and that header, since a `HeadBucket` response has no body to name them.
  - **Retry, then fail:** anything else — an unreachable dependency, a request that doesn't answer, a status that proves neither outcome, a same-region or header-less S3 400 (possibly the transient `RequestTimeout`), S3 credentials that fail to load (possibly a slow EC2/ECS metadata endpoint). These are retried with backoff for up to 60 s per check (`BOOT_PROBE_DEADLINE_MS`), then boot fails with the last reason.
  - **Attempt bounds:** each attempt is aborted after 5 s (`BOOT_PROBE_ATTEMPT_TIMEOUT_MS`) or at the deadline, and calls that ignore the signal in part of their work are raced against it. The first check to fail cancels the others running alongside it, which stop at once instead of retrying for a boot that has already failed; `runBootChecks` settles only after they have stopped, then rethrows the first failure. Every `BootCheckError` message and logged retry reason has `user:password@` scrubbed from any URL it quotes, up to the last `@` before the host. Another attempt is made only if it would still get a second to run — checked again after the wait, since a timer can wake late — so the last real reason is the one reported, and the deadline runs on a monotonic clock. The clock is injected, so the retry and timeout paths are unit-tested without waiting.
- **Logged probe URLs** drop query strings, fragments and userinfo, and the Inngest event key is redacted; a credential in a path segment is not detected.
- **Dev and test:** the Hindsight containers enforce a fixed test key, so every integration and e2e run exercises the authenticated path. `checks.integration.test.ts` pins the probe premises against the pinned images — keyed `inngest start` refuses both anonymous probes, `inngest dev` refuses neither — and `version-pins.test.ts` keeps its Inngest image equal to the dev harness's.

Keys do not cover every route. Inngest v1.41.1 serves its dashboard and GraphQL API — including the `invokeFunction` and `rerun` mutations — without auth unless started with `--no-ui`; Hindsight 0.9.1 serves `/health`, `/version`, `/metrics` and `/docs` without auth. `DEPLOYMENT.md` → *Securing internal services* covers the deployment side: `--no-ui`, private ports 8288/8289, Redis and Postgres passwords, and keys generated once.

**Breaking:** `cogmo serve` requires `HINDSIGHT_API_KEY` with a matching `ApiKeyTenantExtension` on Hindsight and, unless `INNGEST_DEV` is set, Inngest keys matching a keyed `inngest start`. A dependency that stays unreachable for 60 s fails boot instead of logging a warning, service URLs with embedded credentials are rejected, and so is a half-set S3 key pair.
