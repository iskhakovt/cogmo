Git's background maintenance stays opt-in per call site rather than being suppressed inside the shared `runGit` helper, and the reasoning now lives next to the helper so the next reader doesn't take the tempting shortcut.

`git commit` and `git push` each spawn a detached `git maintenance run --auto` that keeps writing after the command returns. Whether that is a hazard or the whole point depends on the repository rather than the command: it is a hazard exactly where the tree is about to be deleted, and desirable everywhere else. The setting therefore belongs to a repo's lifecycle, which is how git scopes it too — `git maintenance register` works by writing `maintenance.auto=false` into the repo it registers. A helper that knows the command and the credentials but never which kind of tree it is pointed at is the wrong place to decide.

Every caller but one targets a repo that outlives the command — the parent repo behind `git-as-transport`, the registry clone `repos.add` creates, the skills repo — where keeping them packed is what maintenance is for. The exception, teardown's WIP push, passes the settings itself through `opts.env`.

Two details recorded for whoever needs this next, both measured against git 2.54 rather than inferred. `maintenance.auto=false` is the setting that stops the spawn; `gc.auto=0` alone does not, since it gates the work the spawned process finds to do rather than the spawn itself. And `gc.autoDetach=false` is the knob for wanting a repo maintained but not written to behind your back — it runs the same maintenance with `--no-detach`, so it completes before the command returns instead of being turned off.

That `opts.env` passthrough is therefore load-bearing rather than incidental, so it gains a test: a config key set only through that argument is visible to the spawned git, and absent it the same lookup fails. The key is deliberately not `gc.auto`, which `vitest.config.ts` injects into every tier — a control case reading that would have proved nothing.
