Git's background maintenance stays opt-in per call site rather than being suppressed inside the shared `runGit` helper, and the reasoning now lives next to the helper so the next reader doesn't take the tempting shortcut.

`git commit` and `git push` each spawn a detached `git maintenance run --auto` that keeps writing after the command returns. That is a hazard in exactly one situation: the tree it writes into is about to be deleted, which is what teardown does to a task worktree. Every other caller of `runGit` targets a repo that outlives the command — the parent repo behind `git-as-transport`, the registry clone `repos.add` creates, the skills repo — and keeping those packed is the point of maintenance, not a race. Suppressing it in the helper would tax seven call sites to serve one, and that one already passes the settings itself through `opts.env`.

That `opts.env` passthrough is therefore load-bearing rather than incidental, so it gains a test: a config key set only through that argument is visible to the spawned git, and absent it the same lookup fails. The key is deliberately not `gc.auto`, which `vitest.config.ts` injects into every tier — a control case reading that would have proved nothing.
