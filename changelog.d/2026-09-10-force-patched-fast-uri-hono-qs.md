**`pnpm-workspace.yaml` carries advisory floors for `fast-uri`, `hono` and `qs`.** All three reach the production tree only as transitives — `fast-uri` under `ajv`, `hono` under `@modelcontextprotocol/sdk` and `inngest`, `qs` under `express` and `body-parser`. Each parent's declared range already admits the patched version, so the floors don't force anything a parent hasn't sanctioned; they stop a lockfile resolution from sitting below the patch line, which is the state `pnpm audit --prod` was reporting: four high `fast-uri` advisories, three moderate `hono`, two moderate `qs`.

The floors are the right instrument rather than a lockfile refresh because nothing pins these packages. No manifest names them, so Dependabot — which bumps manifest entries — has no edge to walk, and its alerts for all nine sit open with no PR attached. A bare `pnpm update` moves `fast-uri` and `hono` but leaves `qs` on the version already in the lockfile, since pnpm keeps a satisfying resolution when the range still admits it. An explicit floor is the only form that survives the next unrelated lockfile churn.

`fast-uri`'s floor is capped below 4. `ajv` declares `fast-uri@^3.0.1`, and an unbounded `>=3.1.6` resolves to 4.1.4 — a major the parent never declared support for. The cap holds it at 3.1.7. `hono` (4.13.7) and `qs` (6.16.0) land inside `^4.11.4` and `^6.14.0` / `^6.15.2` without one.

Both ajv consumers — `agent/pipeline/validate.ts` and `skills/runner.ts` — compile inline schemas with no `$id`, `$ref` or `format: "uri"`, which is the whole of ajv's fast-uri surface, so the bump is inert for first-party code. `express`, `hono` and `qs` have no first-party importer at all.

Two dev-tier `esbuild` advisories stay open and are not fixable by the same mechanism. `GHSA-g7r4-m6w7-qqqr` (low, Windows-only dev-server file read) would need `>=0.28.1` against `tsup`'s declared `^0.27.0`; `GHSA-67mh-4wv8-2f99` (moderate) reaches the tree through `drizzle-kit`'s deprecated `@esbuild-kit/core-utils`, pinned at `~0.18.20`. Forcing either violates a declared range to patch a dev server neither `tsup` nor the drizzle loader runs. `drizzle-kit`, `tsup`, `vitest` and `@copilotkit/aimock` are all devDependencies, so neither advisory reaches the production tree and `pnpm audit --prod` is clean.
