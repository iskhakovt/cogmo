A steering rule's lifecycle is the pgEnum `steering_rules.status` — `live`, `learning`, `disabled`, `retired` — rather than an `active` flag read together with `retracted_at` and `source`. The state machine is in `design/evolution.md` → Explicit Instructions → Lifecycle: the transition table, and a failure-mode table covering a switch against a graduation, retiring a retired rule, a retirement during a merge, the backfill and a run across the deploy. `chk_steering_rules_lifecycle` holds each status to its sources (a learned rule is live, learning or retired; an operator's rule or a channel default is live, disabled or retired; an instruction is live or retired) and `retracted_at` to the retired status, so a source change can no longer re-read a disabled operator rule as a learning one. One migration, `0076_steering_rule_status`, in one transaction: the type and the column, the backfill from `(active, retracted_at, source)`, `SET NOT NULL`, `uq_steering_rules_instruction` rebuilt on `status = 'live'`, `DROP COLUMN active` and the CHECK — a row the CHECK refuses rolls the file back for the next boot to retry.

In the store every read filters on `status`, and a graduation is its own conditional UPDATE (`WHERE status = 'learning'`) whose outcome, `transitioned` or `stale`, `upsertCorrection` matches exhaustively — so a reinforcement of a live `evolution` row whose count crosses 2 no longer reports a promotion. `RuleMatch`, `ReviewedRule` and `ExtractionRule` carry `status`; `listRules` leaves a disabled rule out, as before. `migration-0076.test.ts` runs the file over every `(active, retracted_at, source)` combination the old CHECK allowed and asserts the status each lands in, the rollback on a row it can't place, the new CHECK's source×status matrix, the rebuilt index, and the store's reads; the 0059 and 0067 migration tests keep their pre-migration shape with `active` put back and `status` defaulted. The store test pins the two behaviours the status fixes, both red against the flag encoding.
