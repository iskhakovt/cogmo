Image generation gets three follow-up improvements that close the gaps left by PRs #220 / #222: hot-reload on wizard / CLI CRUD, reference-image (image-to-image / kontext) support, and a wizard step for `openai_compatible` image providers.

**Hot-reload.** Boot no longer builds the `generate_image` tool from a one-shot DB read. A new `ImageToolsLoader` (`src/agent/image-tools-loader.ts`) re-queries `image_providers` + `image_models` on every `handle-message` turn and rebuilds the Zod model enum + tool description from the current rows; provider adapters (`buildImageProvider` output) are memoized inside the loader by row id, so we only decrypt + construct each SDK client once per process. `handle-message` splices the loader output into the per-turn built-ins set alongside skill and MCP tools, so wizard / CLI CRUD takes effect on the next message rather than the next restart. The "Restart `cogmo serve` for the change to take effect" lines on `cogmo image-provider add`/`remove` and `cogmo image-model add`/`remove` are gone — they were lies after this change. Same hot-reload shape is still on the backlog for `LlmProviderResolver` and the voice provider; this is the pattern they'll follow.

**Reference image (kontext / image-to-image).** `ImageModelCapabilitiesSchema` gains `imageInput: "required" | "optional"` (JSONB field, no migration). The `generate_image` tool surfaces a new optional `referenceImage` field — value is an `AttachmentStore` path (`inbound/<id>.png` for a user upload, `generated/<id>.png` for a previously-generated image). The handler downloads the bytes via `attachments.download(path)` and forwards via the AI SDK's `prompt: { text, images }` shape — validated only against `kind: "fal"` today (the kontext line). For `kind: "oai"` the handler returns a text error pointing the LLM at a fal model; future support for OpenAI's gpt-image-* edits is gated behind the still-open todo for a dedicated `openai` provider type. The `fal/flux-kontext` seed row gains `imageInput: "required"` so the model is finally usable — pre-this-PR it was advertised in the catalog but the tool schema accepted no reference and every kontext call returned HTTP 422. Three text-recoverable error shapes are surfaced for the LLM to act on: required-but-missing (re-call with a path), supplied-but-unsupported (pick a different model or drop the field), supplied-to-non-fal (pick a fal-backed edit model). The tool description picks up per-model `[needs reference image]` / `[optional reference image]` annotations so the LLM knows which models accept the new field.

**Wizard step for OpenAI-compatible image providers.** `stepConfigureImageProviders` (`src/setup/wizard.ts`) lands as a new wizard step, paralleling the existing `stepConfigureProvider` (LLM providers). Loops "add another image provider?" against the live `image_providers` list, picks `openai_compatible` only — fal stays in the existing `stepConfigureOptionalTools` API-key prompt to avoid duplication, since the boot-time `ensureFalImageDefaults` seed wires the canonical 9-model fal catalog automatically. The new step collects name + base URL + key, then loops `promptAddImageModels` (name, model-string, description, ratios, seed, image-input). Reuses the same `agentStore.createImageProvider` / `createImageModel` calls that back the `cogmo image-provider` / `cogmo image-model` CLI commands — no behaviour drift between wizard and CLI.

The CLI `cogmo image-model add` gains a matching `--image-input required|optional` flag, and `cogmo image-model list` adds an `image_input` column. Unit coverage: 5 new `image-tools.test.ts` cases for the reference-image gating + forwarding paths, 2 new `image-model.test.ts` cases for the new flag, a new `image-tools-loader.test.ts` covering cache hit / add-reflected / evict-on-delete / empty-catalog. `design/image-generation.md` upgraded to reflect the new per-turn loader posture and the reference-image surface; the todo entry tracking image hot-reload (`p3` Image provider/model hot-reload after wizard CRUD) is dropped.
