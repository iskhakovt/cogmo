**A skill deploy's deny and approve report what they resolved, and approve writes nothing before its guard.** `denyPendingDeploy` is one conditional `UPDATE … WHERE status = 'pending_approval'` returning `transitioned`, `not_found`, or `not_pending` with the status the row holds. `runner.denyDeploy` returns `Result<void, DenyDeployError>`; `cogmo skills deny` exits 1 naming the miss (`deploy not found: <id>`, `deploy <id> is not pending: status is 'live'`) rather than printing `"status": "denied"` for an id it never touched; `transport.skills.denyDeploy` maps the two misses onto `skill_deploy_not_found` and `skill_deploy_not_pending` from the runner's outcome, with no read ahead of it. `executeApprove` runs its `pending_approval → live` UPDATE as the transaction's first write, so a zero-row match returns `deploy_not_pending: status is '<status>'` with the `skills` row and `main` untouched. The deny reason stays a log line, written with the transition.

`design/skills.md` gains the deploy lifecycle's transition and failure-mode tables (`[proposed]`). Store tests cover each deny outcome and an approve whose row is resolved between its reads and its guarded write — a Proxy on the transaction runs the deny right before that UPDATE, the interleaving one PGlite connection cannot otherwise produce; CLI tests pin exit 1 for both misses.
