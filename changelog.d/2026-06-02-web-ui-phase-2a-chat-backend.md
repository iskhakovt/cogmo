Stand up the web chat backend — the inbound + live-streaming half of the UI server. A `WebUiAdapter` (a pure SSE `StreamingAdapter`) joins the DeliveryRouter's adapter map and writes each `StreamEvent` of a turn straight to the browser tab's open `text/event-stream` connection. The bridge is a process-local `WebStreamRegistry` keyed by per-tab `platformAddress`: the SSE route registers a tab's connection, the adapter writes through it. Since the Inngest loop and UI server share one process, no broker is involved. Dedup is keyed by `(runId, platformAddress)` so one conversation fans out to every tab watching it.

Three auth-gated chat routes land in the UI server: `POST /api/chat` (create a conversation), `GET /api/chat/:cid/stream?tab=T` (bind the tab's session to the conversation with `receive:"all"` and open the SSE), and `POST /api/chat/:cid?tab=T` (emit a user turn — the response streams back over the SSE). The stream open is the single session owner and closes the session on disconnect so abandoned tabs don't accumulate. Web tabs watch the whole conversation via a new per-channel `sessionReceive` default on the Transport (`"all"` for web, `"routed"` elsewhere) — so multiple tabs on one conversation all receive its stream, not just the tab that sent the turn.

`AdapterSetupResult.adapter` widens to `Adapter | StreamingAdapter` (the web channel is streaming-only; the DeliveryRouter already skips pure-streaming adapters in `notifyConversation`). Phase 2a streams live only — a mid-stream disconnect loses the in-flight deltas and recovers the completed turn from history on reload; `Last-Event-ID` replay is Phase 2b. The chat SPA that renders this is the next slice.
