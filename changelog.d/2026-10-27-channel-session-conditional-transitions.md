**Channel sessions are an explicit state machine.** `design/transport/sessions.md` → Lifecycle names the unit (`channel_sessions.id`), the two states, the transitions — create, supersede, resume, close — and a failure-mode table: two inbounds on one lazy rotation, two opens racing on an address, a stale close, a scheduled fire rotating onto a chat under a boundary hold, duplicate active rows at deploy, a process on the old code during the migration.

The schema enforces the one invariant snapshot isolation cannot: `0075_sessions_one_active_per_address` adds `uq_sessions_active_address`, a partial unique index on `channel_sessions (channel_id, platform_address) WHERE status = 'active'`, after `0074_sessions_close_duplicate_active` closes every active row but the newest per address. Every open is one store write, `swapSession`: close the address's active row, then a keyed insert (`ON CONFLICT DO UPDATE` no-op SET, `RETURNING (xmax = 0)`) so a loser retries past `40001` instead of raising `23505`. `closeSession` is a conditional transition returning `closed`, `stale` with the row's status, or `not_found`.

Each transition is a use case under `src/transport/sessions/`, shared by `Transport` and the boundary resolver. `Transport.createConversation` joins the address's active session (`kind: "joined"`) or, with `supersede: true`, closes it and opens the fresh conversation in one transaction — `/new` is that one call. `conversations.create` opens a conversation with no session, so the Web UI's new-chat leaves the tab's stream session alive until the new stream resumes onto it. `resolveSession`'s lazy rotation runs lookup, idle check and close in one transaction. `/end` reports a `stale` close as "already ended"; the other closers log one.

`channel_sessions.expires_at` has no writer: the session lookup ignores it, and `todo.md` records that a writer must come with an explicit state.
