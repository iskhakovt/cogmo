A skills-repo coding task whose pushed tip register's dry run refuses now gets a fix pass instead of failing. The task moves to the new `pending_fix` status, and a fresh execute session starts on the same branch. Its prompt holds the goal, the approved plan, register's findings and the token budget left. It commits on top, verify runs again, and the dry run judges the new tip. There are at most two fix passes per task, counted in `coding_tasks.presubmit_fix_passes`. When they run out, or a pass leaves the tip unchanged under the same release (a repeated refusal), the task fails `presubmit_refused` as before.

Each pass is its own pair of runs. Claims and the `cli-done` and `verify-complete` event ids are keyed by the pass, so a trigger from an earlier pass loses. The verify run that hands back reaps its sandbox and releases its askpass dir in `teardown-before-fix`, ahead of `coding/task/presubmit-refused`. On git-remote the fix pass fetches the branch and checks out the refused sha, and an auth refusal on that fetch fails `auth_failed`. A fix pass adds its token usage and cost to the task's. A task that had a fix pass announces any failure in its conversation, with a text detail's end kept to fit Telegram. Migrations 0091 (`pending_fix`) and 0092 (the counter and its CHECKs) ship it.
