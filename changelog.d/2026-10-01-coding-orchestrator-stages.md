The coding orchestrators run as named stages, and a task cancelled during execution stays cancelled.

- **Cancel during execute.** The hand-off to verify wrote `pending_verify` unconditionally, so a task cancelled while `execute-cli` streamed was revived: verify pushed its branch and opened its PR, and the user saw a success banner. The hand-off is a conditional `executing → pending_verify` transition (`transition-pending-verify`); a task that ended under the run has its worktree and sandbox torn down, its stream failed with "Task cancelled while executing.", and no `cli-done` emitted.
- **Stages.** `runCodingTask`, `runCodingExecute` and `runCodingVerify` (400–570 lines each) are short sequences over stage modules: worktree allocation, plan and execute sandboxes and sessions, the plan gate, execute outcomes, verify publish, task failure and an `AskpassLease` that releases on every exit. The status claims live in one transition table (`task-lifecycle.ts`). Step ids, step order, memoized shapes and event ids are unchanged.
- **Expected failures.** `delegate_coding` rejects an unregistered repo, a missing skills repo or no sandbox instead of throwing; the model reads the same text. Verify credentials and publish return `Result`s. A non-`Error` throw records its text as the failure reason, and an error's cause appears in it.
- `CodingOrchestratorDeps.secretsStore` is required.
