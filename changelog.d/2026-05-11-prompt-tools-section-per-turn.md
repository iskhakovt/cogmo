The system prompt's `# Tools` section now renders the **per-turn** tool catalog instead of just the static bootstrap built-ins, so the model can introspect every capability it actually has API access to.

The leak. `DefaultPromptSource` took `toolDefinitions: () => ToolDefinition[]` at construction time, and `src/index.ts` bound it to `tools.definitions()` — the static `createDefaultTools` set (memory / web / file / core / document / delegate / register). Meanwhile `handle-message.ts` was assembling a *different* catalog per turn via `composeTurnTools({ builtIns: [...tools.snapshot(), ...imageTools], skillTools, mcpTools, ... })` and passing that wider set to the LLM API. Net result: `generate_image`, every registered Python skill, and every approved MCP tool were callable but invisible to the model's prompt-level self-description. Symptom in the wild: asked "what can you do?" the bot answered from the prompt's `# Tools` block and listed exactly the 7 built-ins, denying image-gen capabilities Sonnet was about to use.

The fix. `toolDefinitions` moves from `PromptSourceConfig` (constructor) to `AssembleContext` (per-call) — the prompt source becomes a proper pure formatter that takes pre-loaded data and renders, matching the contract its own JSDoc has been promising since the namespace landed. The orchestrator resolves `composeTurnTools` *before* the `assemble-prompt` step.run rather than after, threads `turnTools.definitions()` into `promptSource.assemble({...})`, and reuses the same registry on the API call below — single source of truth, no second composition. `src/index.ts` drops its `() => tools.definitions()` callback. The wider catalog is now snapshotted into Inngest step state alongside the prompt string, which is fine: tool list churn between attempts of the same turn is a few-second window and the prompt's stale view would only be a soft mismatch with `turnTools` (already true for any per-turn input that drifts under retry).

**Within-turn profile dual-read race (drive-by).** The orchestrator was reading the `Profile` row twice per turn — once outside `step.run` as `profileForVoice` (driving voice-mode and the per-turn `composeTurnTools` globs) and again inside `step.run("assemble-prompt", …)` via `loadConversationContext` for `ctx.profile`. Under READ COMMITTED a concurrent `/settings` mid-turn could land between the two reads, leaving the rendered prompt's `# Tools` filter sourced from snapshot A while its `basePrompt` came from snapshot B — a pre-existing race, but the `# Tools` move made it visible to the model rather than purely cosmetic. `loadConversationContext` now accepts the pre-loaded `Profile` as input and returns `{ channelTypes, rules }`; the orchestrator threads `profileForVoice` through both the use case and `promptSource.assemble`. Cross-attempt drift on Inngest retry (cached prompt vs. freshly-read profile on attempt N+1) is a separate, pre-existing characteristic and out of scope here.

`prompt.test.ts` updates the two tool-rendering cases to pass `toolDefinitions` via the assemble call and adds an omitted-section case for the new `undefined` default. `handle-message.test.ts` gains five tests under `per-turn tool catalog flows into promptSource.assemble` pinning that image / skill / MCP tools each surface in the assemble arg, that an empty `profile.toolSet` produces an empty `toolDefinitions`, and that the catalog passed to assemble matches the registry handed to `runStreamingAgentLoop` (single source of truth). The `load-conversation-context.test.ts` suite drops its profile-loading case in favour of one asserting the function *doesn't* re-read the profile, plus an `undefined`-profile case.
