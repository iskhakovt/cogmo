`SandboxClient.create` now accepts a discriminated `WorktreeSpec` — `{type:"host-path";hostPath}` for Local-Docker bind mounts, `{type:"git-remote";url;branch;auth}` for backends that clone inside the sandbox. Consumers pick the variant by branching on `capabilities.workingTreeTransport`; the type checker enforces backend/spec match. Daytona's `create()` lifts the Phase-3a worktree/askpass guards: a `git-remote` spec triggers `sandbox.git.clone(url, "/workspace", branch, undefined, username, password)` through the SDK, and a populated `SessionSpec.askpass` triggers `fs.uploadFiles` of the four-file bundle (`helper`/`pat`/`signing-key`/`signing-key.pub`) followed by `fs.setFilePermissions` to `provisionAskpass`'s host modes (755/644/600/644 — the 600 on the signing key is non-negotiable, `ssh-keygen -Y sign` refuses anything broader). Both post-create steps run inside a try/catch that calls `sdkSandbox.delete()` on failure so a half-provisioned sandbox doesn't orphan against Daytona's per-sandbox billing. Foundation only — the coding orchestrator still wires against Local-Docker until Phase 3b.2 adds the host-side `pushTaskBranchToRemote` helper, the `worktreeAssignment.worktreePath`-optional schema change, and the capability-aware orchestrator branching.
