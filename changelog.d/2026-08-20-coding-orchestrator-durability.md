**The coding orchestrators are durable under Inngest's per-boundary replay model.** Inngest re-invokes a function's whole body at every step boundary on success, so a task's re-entry guard has to be a conditional-UPDATE step whose memoized result the body branches on. A bare-body `task.status !== "pending_verify"` read sees the `verifying` the run itself wrote one boundary earlier, abandons the sequence, and leaves the task non-terminal with no failure event for `coding-task-reconcile` to act on. All three orchestrators now open with that step — `claim-task-planning` (`queued → planning`), `set-status-executing` (`awaiting_approval → executing`), `set-status-verifying` (`pending_verify → verifying`) — placed where a run that loses the race returns *before* the failure/teardown machinery, since every check past that point can mark a task failed and a duplicate event must not do that to a row another run owns.

For the plan orchestrator that claim also closes the one place a duplicate `coding/task/start` was expensive: its next moves are `sandbox.create` and a billable claude session. `delegate`'s emit now carries a `task-start-<taskId>` idempotency id, matching the ids the orchestrators already use — the id collapses a re-send inside the bus's 24h window, the transition holds outside it.

Every expensive or irreversible unit is a step for the same reason. `plan-cli` and `execute-cli` hold the billable claude sessions; the plan session has no `--resume`, so a bare-body call replans from scratch and re-renders the whole plan into the user's message once per remaining boundary. `run-verify` holds the repo's test suite, `commit-and-push` the commit and push, `read-head-sha` the HEAD read that pins the PR head, `notify-plan-finalized` the plan-message render. `open-pr` matters most: a second `pulls.create` returns 422 `validation_failed`, which the orchestrator reads as a failure, so a re-POST lets the run that just opened a PR mark its own task `failed`. Progress pushes fire live from inside the step bodies and are suppressed on replay — one run's worth of streaming, which is what a single edited-in-place Telegram message wants. Every CLI-result branch reads a memoized value, so the step graph is identical on every invocation.

Session handles can't cross a step boundary, so each orchestrator resolves `sandbox.resume` through a lazy per-invocation memo inside the step bodies that need one: a live provider call, paid for in proportion to container work rather than replay count. Secrets stay out of Inngest's state store — the PAT reaches `runCommitAndPush` and `runOpenPr` as a closure argument, never a step argument or return. The three broad `catch` blocks now state why they are broad: `status=failed` plus `coding/task/failed` is these functions' designed failure channel, `StepError` from a permanently-failed step included.

Coverage: `orchestrator.replay.test.ts` and `verify-orchestrator.replay.test.ts` drive the real functions through `@inngest/test`, whose engine reproduces the per-boundary model rather than simulating a retry. They pin one CLI session, one suite run, one push and one PR per task; a replay resuming past the status its own step wrote; a duplicate start event returning `skipped` without calling `sandbox.create` or `backend.plan`; a duplicate cli-done event skipping without touching `updateTaskStatus`; a memoized verify verdict reaching the PR body without re-running the suite; and teardown running once at the end of the run, because a planned-but-unexecuted step hands the body a promise the SDK never settles, so `finally` does not fire on a boundary unwind. Shared fixtures live in `src/test/coding-fixtures.ts`. With the same work in the bare body those counts are 7 suite runs and 4 claude sessions per run.

**Rollout note.** All three functions' step graphs change shape. A coding task in flight across the deploy resumes against the new plan, where the executor can be targeting a step id the new code no longer reaches at that point — that run fails with `Could not find step`, `coding-task-reconcile` marks the row off `inngest/function.failed`, and the task is re-delegated. Bounded to whatever was mid-flight at deploy time. Those same rows carry a NULL `claimed_by_run_id`. Matching strictly on run id would strand exactly the tasks the deploy interrupted, so a claim's UPDATE also matches a row already at its target with no claimant and adopts it — stamping this run. Adoption rather than tolerance is what makes it one-shot: waving NULL through at the caller would leave the column NULL forever, and every later delivery would resume the task with its own sandbox and paid session. The three migrations each add a nullable column, two of them with a unique constraint — no backfill, no table rewrite.

**Submission is idempotent one layer up.** `delegate_coding` runs inside the agent loop's durable `tool-iter<N>-<P>` step, which covers replays but not the at-least-once crash window: the `coding_tasks` row commits, the process dies before Inngest records the step result, and the retried body mints a second task and a second sandbox. `ToolHandler` gains an optional third parameter carrying a `ToolCallContext` — per-call facts, kept out of `Service`, which is the per-conversation capability bundle and the ACL boundary. A handler declared `(input, service)` is assignable to the three-parameter type, so tools that don't need one are untouched.

The key is the turn token, the call's iteration and position, and a canonical digest of the tool name and its normalized arguments. The coordinates are load-bearing and the reason is asymmetric: an *infrastructure* re-execution reuses the step id by construction, so it reuses the coordinates, while a *model* retry does not — `tool-iter*` steps take no Inngest retries precisely so that a fresh tool_use is the retry channel. A key without the coordinates collapses those two, and the model's retry of a failed call replays the cached failure instead of running. The digest covers what the coordinates cannot: a re-delivery replays with an empty step cache, the model re-decides, and a *different* call can land at the same coordinate. The residual runs the other way — a re-delivery that re-decides to a different layout can mint a duplicate — and that is the safe direction, since a duplicate is visible where a swallowed retry is not. The turn token is the batch's low-water mark, which identifies the turn's input and doesn't move; `triggerInboundId` does, since Inngest hands debounce the last event of a burst and another message arriving before the turn succeeds re-fires it over a grown batch. Digesting runs over the value the handler will actually see (`ToolSpec.normalizeInput`, populated by `defineTool` with its own coerce-then-parse pipeline) through the same total RFC 8785 encoder the Class D fingerprint uses, so a stringified nested argument, a dropped field, a cycle or a non-finite number can't fork the key or throw out of the bare body. Never `tool_use_id`, which re-rolls whenever an iteration re-runs.

`CodingService.delegate` threads that key into `coding_tasks.idempotency_key` under a plain `UNIQUE`. `insertOrRecoverTask` writes through `ON CONFLICT DO UPDATE` with a no-op SET, discriminating insert from conflict-update on `xmax = 0` — not the `DO NOTHING` plus re-select the skills precedent uses, which cannot resolve a concurrent loser under the project's REPEATABLE READ default: the winner's row is outside the loser's snapshot, and `DO NOTHING` raises no `40001` for the transactor to retry. The recovery pre-check runs ahead of the admission count, because the row a retry is recovering counts against `max_concurrent_tasks` and the default cap of 1 would otherwise make every retry reject itself. A recovered submission returns the original taskId plus the prior task's real status: a `queued` row is re-emitted, since the prior attempt may have died before its own send and skipping there would trade a duplicate for a permanent stall; a started or terminal one is reported as-is rather than announced as freshly queued. Recovery returns before the send-failure cleanup, which is an unguarded `UPDATE ... WHERE id` that would fail a live orchestration or corrupt a finished one. Unkeyed callers (CLI, evolution triggers) are unaffected — Postgres treats nulls as not-equal under a unique constraint.

`schedule_task` is keyed the same way — `scheduled_tasks.idempotency_key` (migration 0053) and `createOrRecoverScheduledTask`, with recovery ahead of both the per-user cap and the `runAt` validation, since the crash retry a key exists for is exactly the one that arrives after its own scheduled time. Its duplicate is the worst on the durable-tool list: a second row fires on every tick from then on, and only an explicit `remove_task` stops it. Skill tools are keyed too, forwarding to `runner.invoke`'s `recovery_point` state machine; a keyed retry whose prior attempt died mid-execute is refused rather than re-firing arbitrary Python, and that refusal now reaches the model as a named verdict carrying the run id instead of a raw exception. `design/crash-recovery.md` → Tool durability policy records the disposition for every other durable tool, including the residuals left standing.

`design/coding-delegation.md` → Inngest step boundaries carries the durability story, the guard-placement rule, and the submission-idempotency contract. `.claude/rules/inngest.md` picks up the guard-placement clause, the durable-is-not-exactly-once rule, and the boundary-unwind semantics.
