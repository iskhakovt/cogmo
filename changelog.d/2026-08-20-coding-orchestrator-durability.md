**The coding orchestrators are durable under Inngest's per-boundary replay model.** Inngest re-invokes a function's whole body at every step boundary on success, so a task's re-entry guard has to be a conditional-UPDATE step whose memoized result the body branches on. A bare-body `task.status !== "pending_verify"` read sees the `verifying` the run itself wrote one boundary earlier, abandons the sequence, and leaves the task non-terminal with no failure event for `coding-task-reconcile` to act on. All three orchestrators now open with that step — `set-status-planning` (`queued → planning`), `set-status-executing` (`awaiting_approval → executing`), `set-status-verifying` (`pending_verify → verifying`) — placed where a run that loses the race returns *before* the failure/teardown machinery, since every check past that point can mark a task failed and a duplicate event must not do that to a row another run owns.

For the plan orchestrator that claim also closes the one place a duplicate `coding/task/start` was expensive: its next moves are `sandbox.create` and a billable claude session. `delegate`'s emit now carries a `task-start-<taskId>` idempotency id, matching the ids the orchestrators already use — the id collapses a re-send inside the bus's 24h window, the transition holds outside it.

Every expensive or irreversible unit is a step for the same reason. `plan-cli` and `execute-cli` hold the billable claude sessions; the plan session has no `--resume`, so a bare-body call replans from scratch and re-renders the whole plan into the user's message once per remaining boundary. `run-verify` holds the repo's test suite, `commit-and-push` the commit and push, `read-head-sha` the HEAD read that pins the PR head, `notify-plan-finalized` the plan-message render. `open-pr` matters most: a second `pulls.create` returns 422 `validation_failed`, which the orchestrator reads as a failure, so a re-POST lets the run that just opened a PR mark its own task `failed`. Progress pushes fire live from inside the step bodies and are suppressed on replay — one run's worth of streaming, which is what a single edited-in-place Telegram message wants. Every CLI-result branch reads a memoized value, so the step graph is identical on every invocation.

Session handles can't cross a step boundary, so each orchestrator resolves `sandbox.resume` through a lazy per-invocation memo inside the step bodies that need one: a live provider call, paid for in proportion to container work rather than replay count. Secrets stay out of Inngest's state store — the PAT reaches `runCommitAndPush` and `runOpenPr` as a closure argument, never a step argument or return. The three broad `catch` blocks now state why they are broad: `status=failed` plus `coding/task/failed` is these functions' designed failure channel, `StepError` from a permanently-failed step included.

Coverage: `orchestrator.replay.test.ts` and `verify-orchestrator.replay.test.ts` drive the real functions through `@inngest/test`, whose engine reproduces the per-boundary model rather than simulating a retry. They pin one CLI session, one suite run, one push and one PR per task; a replay resuming past the status its own step wrote; a duplicate start event returning `skipped` without calling `sandbox.create` or `backend.plan`; a duplicate cli-done event skipping without touching `updateTaskStatus`; a memoized verify verdict reaching the PR body without re-running the suite; and teardown running once at the end of the run, because a planned-but-unexecuted step hands the body a promise the SDK never settles, so `finally` does not fire on a boundary unwind. Shared fixtures live in `src/test/coding-fixtures.ts`. With the same work in the bare body those counts are 7 suite runs and 4 claude sessions per run.

**Rollout note.** All three functions' step graphs change shape. A coding task in flight across the deploy resumes against the new plan, where the executor can be targeting a step id the new code no longer reaches at that point — that run fails with `Could not find step`, `coding-task-reconcile` marks the row off `inngest/function.failed`, and the task is re-delegated. Bounded to whatever was mid-flight at deploy time. The one migration adds a nullable column and a unique constraint — no backfill, no table rewrite.

**Submission is idempotent one layer up.** `delegate_coding` runs inside the agent loop's durable `tool-iter<N>-<P>` step, which covers replays but not the at-least-once crash window: the `coding_tasks` row commits, the process dies before Inngest records the step result, and the retried body mints a second task and a second sandbox. `ToolHandler` gains an optional third parameter carrying a `ToolCallContext` — per-call facts, kept out of `Service`, which is the per-conversation capability bundle and the ACL boundary. A handler declared `(input, service)` is assignable to the three-parameter type, so tools that don't need one are untouched.

The key combines the turn token, the call's iteration and position, and a canonical digest of the tool name and arguments. The turn token is the triggering inbound id, or the batch's high-water mark on `flush` turns, which carry a null trigger while still processing real input. The digest is what makes the key identify a request rather than a slot: within one run the durable `llm-iter<N>` cache pins the tool_use blocks, but a re-delivery starts a fresh run with an empty step cache, the model re-decides, and a different call can land at the same coordinates. Keys are sorted before hashing so an argument reordering still matches. Never `tool_use_id`, which re-rolls whenever an iteration re-runs.

`CodingService.delegate` threads that key into `coding_tasks.idempotency_key` under a plain `UNIQUE`, and `insertOrRecoverTask` mirrors `SkillStore.startOrRecoverRun`: `ON CONFLICT DO NOTHING` plus a re-select. The recovery pre-check runs ahead of the admission count, because the row a retry is recovering counts against `max_concurrent_tasks` and the default cap of 1 would otherwise make every retry reject itself. A recovered submission returns the original taskId plus the prior task's real status: a `queued` row is re-emitted, since the prior attempt may have died before its own send and skipping there would trade a duplicate for a permanent stall; a started or terminal one is reported as-is rather than announced as freshly queued. Recovery returns before the send-failure cleanup, which is an unguarded `UPDATE ... WHERE id` that would fail a live orchestration or corrupt a finished one. Unkeyed callers (CLI, evolution triggers) are unaffected — Postgres treats nulls as not-equal under a unique constraint.

`design/coding-delegation.md` → Inngest step boundaries carries the durability story, the guard-placement rule, and the submission-idempotency contract. `.claude/rules/inngest.md` picks up the guard-placement clause, the durable-is-not-exactly-once rule, and the boundary-unwind semantics. The deferred skill-tool idempotency item is now unblocked: its DB layer already accepts a key, and the plumbing to hand it one exists.
