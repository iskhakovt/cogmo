**The coding orchestrators stop losing tasks to their own status writes, and stop paying for the CLI once per step boundary.** Inngest re-invokes a function's whole body at every step boundary on success, so `verify-orchestrator.ts`'s `if (task.status !== "pending_verify") return skipped` — sitting above the very step that writes `verifying` — read its own write on the next invocation and abandoned the run. The task then sat in `verifying` with no failure event for `coding-task-reconcile` to act on: a silently stranded task, not a visible error. The execute orchestrator had the identical shape on `awaiting_approval` / `set-status-executing`. Both bare-body guards are gone; the conditional-UPDATE step is now the sole re-entry gate, and it is positioned so a lost race returns before the failure/teardown machinery — otherwise a duplicate event that tripped any error on the way in (a rotated secret, an unreachable dependency) would mark an already-terminal task `failed`.

The expensive and irreversible work moved into steps for the same reason. `plan-cli` and `execute-cli` wrap the billable claude sessions: the plan session carries no `--resume`, so every re-invocation replanned from scratch and re-rendered the whole plan into the user's message — a fresh paid CLI run per boundary. `run-verify` wraps the repo's entire test suite, `commit-and-push` the git push, `read-head-sha` the HEAD read, and `open-pr` the GitHub PR creation. That last one was the sharpest edge: a second `pulls.create` returns 422 `validation_failed`, which the orchestrator reads as a failure, so the run that had just opened a PR would go on to mark its own task `failed`. Session handles can't cross a step boundary, so each orchestrator resolves `sandbox.resume` through a lazy per-invocation memo inside the step bodies that need it, making provider round-trips scale with container work rather than with replay count. Progress pushes fire live from inside the step bodies and are suppressed on replay — one run's worth of streaming, which is what the Telegram progress message wants. Every CLI-result branch now reads a memoized value, so the step graph is identical on every invocation.

Measured against the pre-change code through `@inngest/test`, whose engine reproduces the per-boundary model: a single verify run executed the repo's test suite **seven times**, and a single plan run spawned **four** claude sessions. The new `orchestrator.replay.test.ts` and `verify-orchestrator.replay.test.ts` pin one CLI session, one suite run, one push, and one PR per task, plus the two re-entry contracts — a replay resumes, a genuinely duplicate event still skips.

`design/coding-delegation.md` → Inngest step boundaries now describes what the code does: the streaming rows are durable steps rather than "can't replay a stream", the stale `wait-for-approval` `step.waitForEvent` row is replaced by the separate-function hand-off that actually ships, and the re-entry-guard placement rule is stated alongside. `.claude/rules/inngest.md` gains the placement clause on its existing "never gate the bare body on state your own steps mutate" rule.

**Rollout note.** All three functions' step graphs change shape. A coding task in flight across the deploy resumes against the new plan, where the executor can be targeting a step id the new code no longer reaches at that point — that run fails with `Could not find step`, `coding-task-reconcile` marks the row off `inngest/function.failed`, and the task is re-delegated. Bounded to whatever was mid-flight at deploy time; no migration needed.
