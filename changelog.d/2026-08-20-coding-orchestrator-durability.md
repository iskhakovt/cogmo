**The coding orchestrators are durable under Inngest's per-boundary replay model.** Inngest re-invokes a function's whole body at every step boundary on success, so a task's re-entry guard has to be a conditional-UPDATE step whose memoized result the body branches on — a bare-body `task.status !== "pending_verify"` read sees the `verifying` the run itself wrote one boundary earlier, abandons the sequence, and leaves the task non-terminal with no failure event for `coding-task-reconcile` to act on. All three orchestrators open with that step — `set-status-planning` (`queued → planning`), `set-status-executing` (`awaiting_approval → executing`), `set-status-verifying` (`pending_verify → verifying`) — and each sits where a run that loses the race returns *before* the failure/teardown machinery: ownership is claimed first, because every check after it can mark the task failed, and a duplicate event must not be able to do that to a row another run owns.

The plan orchestrator's claim also closes the one place a duplicate `coding/task/start` was expensive: its next moves are `sandbox.create` and a billable claude session, and nothing stood between a re-delivered event and both. `delegate`'s emit now carries a `task-start-<taskId>` idempotency id, matching the `task-failed-` / `plan-approved-` ids the orchestrators already use — the id collapses a re-send inside the bus's dedup window, the transition holds outside it.

Every expensive or irreversible unit is a step for the same reason. `plan-cli` and `execute-cli` hold the billable claude sessions — the plan session carries no `--resume`, so a bare-body call replans from scratch and re-renders the whole plan into the user's message once per remaining boundary. `run-verify` holds the repo's test suite (`runVerifyStreaming` caps its captured output at 8 KiB, so the step return stays small), `commit-and-push` the commit + push, `read-head-sha` the HEAD read that pins the PR head, `open-pr` the PR creation — that last one because a second `pulls.create` returns 422 `validation_failed`, which the orchestrator reads as a failure, so a re-POST lets the run that just opened a PR mark its own task `failed`. `notify-plan-finalized` holds the plan-message render, which two trailing boundaries follow on the auto-approve path. Progress pushes fire live from inside the step bodies and are suppressed on replay, which is what a single edited-in-place Telegram message wants. Every CLI-result branch reads a memoized value, so the step graph is identical on every invocation.

Session handles can't cross a step boundary, so each orchestrator resolves `sandbox.resume` through a lazy per-invocation memo inside the step bodies that need one: a live provider call, paid for in proportion to container work rather than to replay count. Secrets stay out of Inngest's state store — the PAT reaches `runCommitAndPush` and `runOpenPr` as a closure argument, never a step argument or return. The three broad `catch` blocks now state why they are broad: converting everything they see, a permanently-failed step's `StepError` included, into `status=failed` plus `coding/task/failed` is these functions' designed failure channel.

Coverage: `orchestrator.replay.test.ts` and `verify-orchestrator.replay.test.ts` drive the real functions through `@inngest/test`, whose engine reproduces the per-boundary model rather than simulating a retry. They pin one CLI session, one suite run, one push and one PR per task; a replay resuming past the status its own step wrote; a duplicate start event returning `skipped` without calling `sandbox.create` or `backend.plan`; a duplicate cli-done event skipping without touching `updateTaskStatus`; a memoized verify verdict reaching the PR body without re-running the suite; and teardown running once at the end of the run — the last one because a planned-but-unexecuted step hands the body a promise the SDK never settles, so `finally` does not fire on a boundary unwind. Shared fixtures live in `src/test/coding-fixtures.ts`; the store fake's reads observe its own writes, which is the property that makes the hazard visible at all. With the same work in the bare body those counts are 7 suite runs and 4 claude sessions per run.

**Rollout note.** All three functions' step graphs change shape. A coding task in flight across the deploy resumes against the new plan, where the executor can be targeting a step id the new code no longer reaches at that point — that run fails with `Could not find step`, `coding-task-reconcile` marks the row off `inngest/function.failed`, and the task is re-delegated. Bounded to whatever was mid-flight at deploy time; no migration needed.
