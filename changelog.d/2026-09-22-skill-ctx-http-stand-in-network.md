**`ctx.http` takes an injectable network, and the skill-authoring integration test uses it.** `DefaultCtxHandler` accepts a `fetch` alongside its existing `resolveHost`. `SkillRunnerOptions.ctxHttp` passes both to every handler the runner builds, and a test reaches that through `BootstrapOptions.skillCtxHttpOverride`. Production leaves all three unset, so it gets real DNS and the global `fetch`, looked up per call. The runner hands the same handler to both tiers, so the override covers `ctx.http` in tier 2 as well; a tier-2 skill's own sockets stay on the real network.

`skill-authoring.integration.test.ts` passes in a stand-in network. It resolves `api.coingecko.com` to a public address and serves the one price endpoint that the authored `btc-spot` skill calls. It applies in record mode as well as replay. The cassettes cover the chat and the Daytona sandbox but not the skill's own request, so without the stand-in the suite depends on CoinGecko's uptime and its rate limits on datacenter IPs, and fails offline. The test asserts that the skill's output equals the stand-in's figure exactly. That figure is 64,725, the price in the recorded reply, and the match only holds if the request stayed in the test process.

The seam needs both halves, and its type requires both. A stand-in `fetch` alone still leaves the address guard resolving `api.coingecko.com` through real DNS. A resolver alone is worse: the guard passes on the resolver's answer while the global `fetch` connects wherever the name really points. The runner passes the two fields by name rather than spreading the object, so nothing else a caller's object carries can replace the handler's manifest or audit binding. A loopback stub server cannot stand in either. A manifest can list `127.0.0.1` in `network.allow`, but the resolved-address check refuses loopback, link-local and private addresses, and reaching a local server would take a resolver that misreports its address: a way around the guard, not a run through it. The allowlist and address checks run unchanged against whatever the stand-in answers, so it replaces the network, not the policy. A unit test pins that a refused destination never reaches an injected `fetch`.

No fixtures change, and no re-record is needed.
