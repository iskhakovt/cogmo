**`pipeline_runs.failure_reason` is an enum tied to the run's status, and the run lifecycle is a documented state machine.** The reason was free text built from interpolated messages, and the gate resolver's failure handler recognised the failure it had committed by comparing that text — coupling recovery to a message's wording, and crediting any gate's failure that carried the same text. The column is now `pipeline_run_failure_reason`, with the variable part (an error class, a degrade reason, schema errors) in `failure_detail`, and both failure handlers recognise their own failure by reason and cursor. The stage runner fails a run only while it still sits on the failing stage, so a delivery the run has moved past no longer fails a healthy run, and a failure it committed before its step was recorded still sends its notice. Two CHECKs make the half-states unrepresentable: a reason is present exactly when the run is `failed` or `cancelled` and belongs to that status, and a run parked on a gate never holds the claim on it; the advance guard requires `running`, so a parked run leaves only through a gate claim. One migration adds the type, backfills every recorded text onto its label with the text kept as the detail, and casts and constrains, all in one transaction. `design/pipelines.md` gains the run's state diagram, transition table and failure-mode table.
