Skills `/disable`, `/enable`, `/skills` Telegram commands (P3.3 slice A). Operator surface for soft-disabling and re-enabling installed skills directly from chat — the kill switch needed before the AST-based risk classifier (slice B) can ship without leaving the operator unable to shut down a misclassified skill in flight. `/skills` lists every registered skill (enabled + disabled) with tier, risk tier, and short git sha — the discovery surface for the other two commands.

`/disable <name>` thin-wraps the existing `SkillRunner.deregister` RPC: soft-disable, preserves the audit trail in `skill_deploys` and `skill_runs`. `/enable <name>` is new — the runner already had `setSkillDisabled(false)` at the store layer, but no public RPC over it. Idempotent in both directions: enabling an already-enabled skill returns `already_enabled` rather than erroring; disabling an already-disabled one is a no-op via the underlying setter.

Approval-gate guard: `enable` refuses when no `skill_deploys` row exists at the skill's current sha with `status='live'`. Without this check, a denied first deploy (`skills.disabled=true`, `skill_deploys.status='denied'` at the rejected sha) could be smuggled past the human approval gate by anyone with operator handle access — `/disable` doesn't strip the rejected sha, and `/enable` would otherwise just flip `disabled=false` and activate the rejected source. The guard surfaces as `skill_no_live_deploy` at the Transport boundary and a "re-register the source via the agent or `cogmo skills register`" message in Telegram. New store method `hasLiveDeployForSkill(skillId, gitSha)` backs the check; rolled-back skills still pass because the prior live deploy row remains.

`SkillRunner` interface gains `enable(opts) → EnableResult` (discriminated union: `enabled` / `already_enabled` / `rejected:not_found` / `rejected:no_live_deploy`) and `listAll()` for the full enabled-plus-disabled projection used by `/skills`. `Transport.skills` namespace gains `list / disable / enable`, all gated through the existing `checkSkillsTapper` identity check. Two new `TransportError` codes: `skill_not_found` and `skill_no_live_deploy`. The Telegram `setMyCommands` registration list picks up the three new entries so they show in the in-client `/` menu.

Tests: 9 new runner-level cases (round-trip, idempotency, unknown name, denied-first-deploy guard, listAll ordering); 5 new store cases (`listAllSkills` ordering, `hasLiveDeployForSkill` matrix across pending/denied/live/different-sha); 12 transport-level cases (`transport-skills.test.ts` — error mapping, identity gating, runner-result-to-Result projection); 15 telegram-level cases (`commands.test.ts` — usage hints, success rendering, alreadyEnabled branch, error mapping, missing-arg behavior). 2,679 unit tests pass, typecheck and lint clean.

Slice B (tree-sitter-based AST risk classifier) lands separately; it depends on a new runtime dep that needs explicit user signoff per the project autonomy rules.
