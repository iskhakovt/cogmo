A Cancel that lands while a coding orchestrator is working stands. The verify run's `verifying → pushed` and `pushed → pr_open` writes (`transition-pushed`, `transition-pr-open`) and every orchestrator's in-run `→ failed` (`transition-failed`, `transition-failed-after-push`) are conditional transitions whose result the run branches on. A task that left its status under the run — a Cancel during the plan or execute session, the verify suite, the push or the PR open — is neither pushed on, nor announced as failed, nor given a PR announcement: the run reclaims its worktree and sandbox and returns `skipped`, leaving the status as the canceller wrote it. A run in flight across the deploy executes each new step once, reads `stale` at the status it had reached, and carries on to the steps it still owes.

Residuals, in design/coding-delegation.md → Task lifecycle: a PR GitHub opened after the Cancel stays open, recorded in `pr_metadata`, with no `pr-opened` event; the catch path's `failed` write stays unconditional; an in-run `failed` whose `emit-task-failed` then exhausts its retries is never announced; and, for one deploy, a verify run that had failed its PR open but not yet announced it stops unannounced.
