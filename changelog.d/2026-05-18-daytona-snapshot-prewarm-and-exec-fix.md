Three Daytona-backend fixes that surfaced together when v1.66.0 lit up real coding-delegation against a freshly-deployed devbase image. They share one PR because they're entangled (snapshot delay masks the exec bug; the exec bug masks the cleanup gap).

**Snapshot prewarm via the named-snapshot API.** `DaytonaSandboxClient.ensureImagePresent(image)` now calls `daytona.snapshot.create({ name, image })` to pre-bake a named snapshot, then `daytona.create({ snapshot })` provisions sandboxes against the runner cache in ~1 s instead of paying the multi-minute lazy `daytona.create({ image })` cost on first task. Snapshot name is derived from the image tag (`ghcr.io/iskhakovt/cogmo-devbase:1.66.0` → `cogmo-cogmo-devbase-1.66.0`); unversioned and `:latest` tags fall back to the lazy `{ image }` path. The call is memoised per image: concurrent callers share one in-flight promise, failures evict the cache so retries are fresh. Boot fires `void sandbox.ensureImagePresent(devbaseImage)` non-blocking so the first task doesn't pay full latency, and the orchestrator's `step.run("ensure-image-present")` awaits the same promise before `create-container` — a task arriving before boot warm completes shares the promise. The state-machine handles `BUILDING`/`PENDING`/`PULLING` (poll until terminal), `ERROR`/`BUILD_FAILED`/`INACTIVE`/`REMOVING` (delete + rebuild), and 404 (build).

**`buildShellCommand` no longer uses bash's `exec` builtin.** The wrapper previously emitted `cd <wd> && env K=V exec <argv>`. The `exec` builtin replaces the shell process with the target binary; Daytona's session-command completion detection fires on the **shell**'s exit, not the target's, so every exec'd command's WebSocket log stream stayed open silently after the target binary exited. PR #267's idle watchdog correctly identified this as 30 s of stdout/stderr quiet and killed every `checkoutFeatureBranchInSandbox` call in `coding-task-start` after v1.66.0 deployed. Dropping the `exec ` prefix lets the shell exit naturally after the child runs — Daytona's completion event fires, the WS closes, `wait()` resolves. Pairs with Daytona [#2513](https://github.com/daytonaio/daytona/issues/2513) (missing async-exit notification). Unit test `exec-streaming.test.ts:164` previously pinned the buggy contract via `expect(command).toBe("exec 'pwd'")`; replaced with a regression test that asserts `buildShellCommand` never emits `\bexec\b`.

**Orchestrator catch-path drops the `containerCreated` gate.** All four call sites (`runCodingTask`, `runCodingExecute`, `runCodingVerify`'s finally) now call `sandbox.deleteByTaskId(taskId)` unconditionally. The gate tracked whether `sandbox.create()` *returned*, not whether *provider-side state existed* — on Daytona, the SDK's 60-second `waitUntilStarted` timeout fires while the snapshot build is still running server-side, leaving a billable sandbox labelled with `cogmo.task` that the gate would refuse to reap. `deleteByTaskId` is contract-bound to be idempotent via the label index, so the unconditional call costs one cheap label query when there's nothing to reap (Local-Docker's atomic create path).

Two tests flipped from "pins no-cleanup-when-throw" to "pins always-cleanup-via-label-sweep" — they were locking in the buggy contract. The unconditional path also surfaces a latent leak fix for Daytona verify: the host-side askpass dir is now wiped whenever `askpassProvisioned` is set, not only when container creation failed (the old `deleteByTaskId` cascade only cleaned up the Local-Docker bind-mount path).

design/sandbox.md gets a new "Snapshot prewarm" subsection documenting the named-snapshot flow, the streaming-exec section captures why `buildShellCommand` runs targets as bash children (not via `exec`), and the deferred list now flags snapshot GC + Daytona-side orphan sandbox sweep as related future work.
