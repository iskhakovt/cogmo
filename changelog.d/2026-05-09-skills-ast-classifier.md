Skills AST-based risk classifier (P3.3 slice B). Replaces the declaration-only stub with a real static-analysis pass over `skill.py`: parses the Python source via tree-sitter, walks for imports + side-effecting call sites, and routes the deploy through three exits — undeclared-dangerous-effect → `rejected` with a per-effect label; declared-or-detected-dangerous → `approve` (human tap required); nothing dangerous declared OR detected → `auto` (no human in the loop, ships immediately). The auto path was unreachable in the stub and is the value-unlock here.

Detection is rule-table-driven (`src/skills/ast-rules.ts`): one row per import-package → effect mapping (`smtplib` → `sends_email`, `subprocess` / `multiprocessing` → `spawns_subprocess`, `stripe` / `plaid` → `financial`, `slack_sdk` / `discord` / `telegram` / `twilio` → `sends_message`) and one row per call-pattern → effect mapping (full `subprocess.{run,Popen,call,check_*}`, `os.{system,popen,exec*,spawn*,fork,posix_spawn}`, `os.{remove,unlink,rmdir,mkdir,chmod,chown,truncate,…}`, `shutil.{rmtree,copy,move,…}`, `pathlib.Path.{write_text,write_bytes}` matched object-anywhere, and `open(..., "w"|"a"|"x"|"+...")` with a string-literal write-mode predicate). Adding a rule is "drop a row" — no logic in the table file.

**This is a UX gate, not a security boundary.** A skill body can `getattr(__import__("os"), "system")(...)` and slip past detection — sysbox isolation, the `effects`-driven secret allowlist (P3.4), and the `approve` tier carry the actual security weight. AST lint exists to (a) force `effects:` in the manifest to track what the body actually does (drift catcher), and (b) prove enough harmlessness to skip the human approval tap (tier promoter). The classifier head comment and the `dynamic / aliased bypass` test block document this explicitly so a future reader doesn't mistake the rule table for a sandbox.

Parser is `web-tree-sitter` (WASM) + `tree-sitter-python.wasm` vendored at `vendor/tree-sitter-python/` (~458 KB, copied verbatim from `@vscode/tree-sitter-wasm@0.3.1` — VS Code's curated bundle, parses Python in millions of installs). Picked over native `tree-sitter` to keep the deploy story single-binary: pure-JS deps, no `node-gyp`, no prebuilt-binary-per-Node-major fragility. Cold-start of the parser (one-time per process) is tens of ms; steady-state parse of typical skill files is single-digit ms — comfortably under the deploy hot path's budget. `vendor/` is added to `package.json#files` and copied into the Docker build stage so production runtime sees the WASM at the expected path.

Failure mode is a fallback: any throw from the AST path (parser load failure, walk panic, missing wasm at runtime) is caught in `classifier.ts` and routes through the existing declaration-only stub — `classifier_version` shifts from `ast-1` to `stub-2-effect-aware` in the audit log so an operator can see the degradation, and the deploy still completes with the conservative declaration-based tier (so the system stays available even if the WASM module is broken in some pathological build).

Tests: 38 fixture-driven cases in `ast-classifier.test.ts` (every detection rule + the false-positive avoidance for comments and string literals + the deliberate-FN dynamic-import case + tree-sitter's error-tolerant recovery on broken Python); the classifier test file split into "live AST path" + "declaration-only fallback" suites (both paths covered). Two new runner.register cases pin the end-to-end behaviour: undeclared-smtplib body rejects the deploy without writing rows, and declared-+-used `sends_email` lands as `pending_approval`. One pre-existing assertion changed from `notify` to `auto` — the `ECHO` skill (no effects, no detectable side effects) was unreachable in the stub but is the canonical auto-tier example now.

2,694 unit tests pass; typecheck + lint clean. The runtime dep is one new package (`web-tree-sitter`) and one vendored WASM file.
