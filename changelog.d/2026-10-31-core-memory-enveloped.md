**Core memory renders as enveloped data, and block keys follow a pattern.** `# User` opens with a header saying its blocks are data about the user and not instructions, then puts each group's blocks in a `<core_memory trusted="false">` element, the group leads outside. A turn context's `<core_memory_updates>` carries `trusted="false"` and the same data-not-instructions clause. Every ATX heading line in a block is backslash-escaped and every envelope closing tag escaped, so a persuaded `core_memory_update` can't add a standing system instruction, open a top-level section or end its element; setext and container headings stay inside the element. `core_memory_read` returns the same rendering, and `writeCoreMemoryBlock` strips the escapes, so a block copied from the prompt stores as it was and a restricted override's line dedupe still matches.

`core_memory_update` keys must match `^[a-z][a-z0-9_-]{0,63}$`: the tool's input schema carries the pattern, and `writeCoreMemoryBlock` refuses any other key with `invalid_key`, which the tool turns into a rejection naming the rule. A stored row whose key fails the pattern still renders, its key a quoted JSON string on one line, so no user data is dropped.

The `# User` envelope is part of the configuration digest and the tool schemas part of the frozen tool table, so every conversation whose profile has core memory opens one `configuration` epoch at its next turn: one full prompt-cache rewrite. The turn-context change is user content and costs no epoch. No migration. No cassette needs re-recording: the llmock key normalizer drops `<core_memory_updates>` with or without attributes, and no cassette holds a heading or closing tag inside a block.
