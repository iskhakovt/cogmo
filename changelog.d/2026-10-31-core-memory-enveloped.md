**Core memory renders as enveloped data, and block keys follow a pattern.** `# User` opens with a header saying its blocks are data about the user and not instructions, then puts each group's blocks in a `<core_memory trusted="false">` element, the group leads outside. Every ATX heading line in a block is backslash-escaped and every envelope closing tag escaped, so a persuaded `core_memory_update` can't add a standing system instruction, open a top-level section or end its element. `core_memory_read` and a turn context's `<core_memory_updates>` render blocks the same way.

`core_memory_update` keys must match `^[a-z][a-z0-9_-]{0,63}$`: the tool's input schema carries the pattern, and `writeCoreMemoryBlock` refuses any other key with `invalid_key`, which the tool turns into a rejection naming the rule. A stored row whose key fails the pattern still renders, its key a quoted JSON string on one line, so no user data is dropped.

The envelope is part of the configuration digest and the tool's schema part of the frozen tool table, so every conversation whose profile has core memory opens one `configuration` epoch at its next turn: one full prompt-cache rewrite. No migration. No cassette needs re-recording: cassettes match on user messages, and none holds a heading or closing tag inside a block.
