**A late reply no longer persists after a newer turn re-batched its inbounds.** A failed turn's retry can run between a younger turn's steps, and the younger turn re-reads every inbound above the last answered cursor. `create-user-message` now records the batch's first inbound on the turn row (`messages.first_inbound_message_id`, migration 0070, NULL on other rows and on older turn rows). In its insert's transaction, `persist-new-messages` returns `persisted` with the newest reply already on its cursor, so a re-run after commit writes nothing. Otherwise, when a later non-pipeline turn row covers the cursor (`TranscriptStore.isCursorRebatched`), it writes nothing and returns `superseded`. The run then skips the emits, delivery, `send-response` and `flush`, and ends `skipped: stale`. A `{ id }` memo from a run in flight across the deploy reads as `persisted`. Residuals, described in design/crash-recovery.md → Late replies: the window before the younger turn row commits, and a superseded reply that has already streamed.
