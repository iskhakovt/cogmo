Raw sandbox lifecycle telemetry on `coding_tasks.resource_usage`. The execute orchestrator now stamps `resource_usage.sandbox` at fresh-create time (`backend`, `created_at`, provisioned `cpu` + `memory_bytes`) and appends `deleted_at` at teardown. Captured Cogmo-side, so it works uniformly across backends — no dependency on per-sandbox usage APIs we don't have. Downstream tooling computes derived quantities: `wall_clock = deleted_at - created_at`, `billable estimate ≈ wall_clock × provisioned × $rate`.

No `cpu_seconds` field stamped — Daytona's SDK v0.173.0 only exposes org/region-level instantaneous quotas (`OrganizationUsageOverview`, `RegionUsageOverview`), not per-sandbox cumulative consumption. The schema is honest about what we can actually capture, no "looks like usage but isn't" field. When upstream adds per-sandbox usage we wire it as a separate slice; tracked under Phase 3c's deferred (e) bucket.

Required a contract change on `CodingStore.setTaskResourceUsage`: was replace-not-merge, now shallow-merge. Top-level fields in the patch overwrite existing values; nested objects (`memory_bytes`, `sandbox`, `provisioned`) are replaced wholesale, not deep-merged. Callers wanting to extend one nested field must load the row first. Implementation does load + spread + write under the caller's transaction — single-orchestrator-per-task ensures no concurrent writers. The prior comment flagged this change as forced once a second writer landed; this is it.

Only the execute-orchestrator fresh-create path writes lifecycle; plan and verify phases are short and not yet captured (would require either a `sandboxes` array on the schema or a phase discriminator). Resume-path executions skip the create stamp by design — the sandbox they re-attach to was already stamped by a prior orchestrator run.
