An attachment of a type the model can't read no longer breaks the conversation it was sent in.

- **Telegram infers a document's type** when `mime_type` is missing or `application/octet-stream`, the type clients send for a file they don't recognise (`.html` among them): from the file name's extension through `mime-types`, then from the content, where valid UTF-8 with no WHATWG binary data bytes in its first 8,000 bytes is `text/plain`. An HTML file or a script in a language the extension table lacks now reaches the model as text, and an image sent as a file with no type still routes to vision. A specific `mime_type` still wins. `mime-types` was already installed through the MCP SDK and Inngest and is now a direct dependency; the text check is Node's `buffer.isUtf8` plus the spec's byte ranges.
- **The Anthropic adapter stubs what it can't send** in place of throwing: a document that is neither PDF nor text-like, or a base64 image that isn't JPEG, PNG, GIF or WebP, becomes a text block naming the file and its type (`[document: page.html (application/octet-stream) — not supported on this provider]`), as the OpenAI-compatible adapter already does for binary documents. The attachment stays in the stored row and replays on every later turn, so the throw failed each of them at `count-tokens-1`. A conversation already stuck this way recovers on its next turn.
