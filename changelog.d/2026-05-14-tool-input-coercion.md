Recover stringified nested object/array tool arguments before Zod validation. Some providers occasionally emit a nested object field as a JSON string (`{"schedule": "{\"kind\":\"one_off\",...}"}`) rather than a JSON object — the outer parse succeeds but Zod then rejects the inner field with "expected object, received string" and the agent loop wastes round-trips on retries the model can't fix.

`defineTool` now walks the tool's JSON Schema before parsing: at every position where the schema unambiguously demands an object or array (direct `type`, or a union whose branches all agree), if the value is a string we attempt one `JSON.parse`. If the parse fails or yields the wrong shape, the string is left in place so Zod still surfaces a genuine type error. Recovery is reported via a debug log (`tool`, `paths`) so production traces show when it fires and which fields hit it.

Unions that legitimately accept strings (e.g. `string | object`) are left alone — coercion only triggers when every branch agrees the value must be a structured type.
