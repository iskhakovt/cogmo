Replaced the per-test Telegram channel marker (`_test: true` credentials sentinel) introduced in PR #197 with an integration-fixture pattern: a localhost HTTP mock server in `test/telegram-mock.ts` that emulates the Telegram Bot API (`getMe`, `getUpdates`, `deleteWebhook`, `setMyCommands`, …) plus a single Telegram channel row seeded once by `test/integration-setup.ts` whose `apiRoot` credential points at the mock. Channel rows now live across the whole integration run instead of being inserted and torn down per test, so `bootstrap()` callers in `cli.integration.test.ts` and `pipeline.integration.test.ts` can iterate `startChannels` cleanly without grammY's "Empty token!" exception leaking out of one file into the next.

Why a localhost HTTP server, not the in-process fetch interceptor pattern used by `fal-mock.ts` and `openai-voice-mock.ts`: `cli.integration.test.ts` spawns fresh Node subprocesses that re-run `bootstrap()` from scratch, and an in-process `fetch` override never reaches a child process. A localhost server reaches both the in-process bot AND every spawned subprocess once the URL is in `channels.credentials.apiRoot` — the URL travels through the DB row, no `TELEGRAM_API_ROOT` env var is needed (the existing Telegram adapter already passes `apiRoot` from credentials into grammY's `client.apiRoot` config). `observer.integration.test.ts` swaps `seedActiveChannelSession` (which inserted a marker channel + a session) for `openActiveChannelSession`, which queries the seeded Telegram channel by type and inserts only the per-test session row, mirroring the pattern `pipeline.integration.test.ts` already uses for the seeded direct channel. The PR #197 `afterAll(cleanupTestState)` and the `_test: true` cleanup line are both gone.
