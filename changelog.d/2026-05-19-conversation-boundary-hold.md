Conversation boundary hold: ask the user before silently rotating onto a fresh conversation.

Before, `resolveSession`'s safety-net detected stale idle on a chat and the next inbound landed in a brand-new conversation with no signal. Hindsight + core memory carried across, but turn-level context didn't — and the user had no affordance to continue the prior thread short of remembering its alias and running `/resume <alias>`.

Industry survey first (separate research thread): every commodity ChatGPT-on-Telegram bot ships `/reset` or `/new` as a stateless wrapper, with either silent or one-liner idle resets. None expose the inverse — a one-tap "pick up where we left off" affordance at the boundary moment. Inline keyboards on bot replies are widespread for settings/permissions; using one at a *conversation boundary* is novel ground, and the only design that addresses the user's complaint without introducing a "first reply generated without context" repair path.

Adopted shape: when an inbound arrives on a stale chat AND the prior conversation accumulated ≥ `BOUNDARY_PROMPT_MIN_USER_TURNS` user turns, the adapter sends a prompt with two inline buttons (`↶ Resume <alias-or-snippet>` / `✦ Start fresh`) and buffers the inbound in a new `boundary_pending` table. Resolution drains the buffer into `inbound_messages` against the chosen conversation, swaps or creates the session, and emits one `inbound/arrived` per buffered row plus a single `boundary/resolved`. The agent never runs in a conversation the user didn't choose, so there are no side effects to reverse.

Why "wait" beats "create eagerly and repair on tap": once the agent runs in the wrong conversation, the produced reply can't be unsent. Repair options all cost something — edit-and-replace is confusing, post-a-second-reply means two answers to one question, leave-as-is means the user's first answer was wrong. Tool calls in the eagerly-created conversation may also be irreversible (memory writes, scheduled jobs). The wait approach pays a bounded latency (defaults to 30s waiter timeout) only on the small fraction of returns the heuristic identifies as worth asking about — exactly the cases where the wrong-context reply would have been most painful.

Schema: new `boundary_pending` table with `UNIQUE (channel_id, platform_address)` — one hold per chat. `platform_user_handle` is stored so the waiter-timeout path (no Telegram callback context) can do identity resolution the same way a button-tap path does. `buffered_inbounds` is a `jsonbZod`-validated array of `{content, platformTs}`; no `channel_session_id` because at hold-creation time the prior session is closed and the new one doesn't exist yet — both get assigned when the buffer drains.

Inngest events: `conversation/boundary/pending` (dedup id `boundary-pending-${boundaryId}` — one waiter per hold) and `conversation/boundary/resolved` (dedup id `boundary-resolved-${boundaryId}`). The new `boundary-waiter` function triggers on `boundary/pending`, sleeps `BOUNDARY_PROMPT_TIMEOUT_SECONDS`, then calls `resolveBoundary` with `kind: "fresh"`, `reason: "waiter_timeout"`. `cancelOn` keyed on `data.boundaryId` ends the wait when the user taps. `resolveBoundary` is idempotent — a button tap that wins the race against the waiter wake leaves the second call returning `boundary_not_found` and no-oping.

`/new`, `/resume <alias>` during a hold are routed through the same `resolveBoundary` use case so the buffered inbounds drain into the user's commanded destination rather than orphaning. `/new <profile>` forwards the explicit profile id; `/resume <alias>` resolves the alias to a conversation id before resolving (same identity + ownership checks as the existing `resumeConversation` path).

Config: `BOUNDARY_PROMPT_TIMEOUT_SECONDS` (default 30) and `BOUNDARY_PROMPT_MIN_USER_TURNS` (default 3) gate the prompt to cases where continuation is plausibly worth a tap. Short gaps and one-shot priors fall through to today's silent fresh-create path. Telegram is the only adapter that wires the prompt UX; the Direct channel ignores `boundary` in `AdapterDeps`.

Design doc: `design/transport/sessions.md` → "Boundary Hold: Resume / Start Fresh Prompt".

Test coverage: 5 PGlite store tests (boundary CRUD, append, UNIQUE collision, idempotent append, peek with prior-turn gate + snippet truncation), 6 use-case unit tests (resume-prior, fresh with chat-default fallback, missing row, access denied, identity rejected), 6 Telegram adapter tests (prompt fired, append on follow-up, fall-through when no substantial prior, both callback paths, "already resolved" toast), 2 command-handler tests (`/new` during hold + `/new <profile>` during hold), 1 `/resume` during hold test.
