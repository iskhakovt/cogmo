The system prompt's `# User` section renders the core memory blocks of the conversation's user, the same user `core_memory_update` writes for. `loadConversationContext` loads the blocks for the conversation's user in the same transaction as the steering rules, inside the `assemble-prompt` step, and `PromptSource.assemble` takes them with the rest of the pre-loaded context, so `DefaultPromptSource` is a pure formatter. `handle-message`, pipeline stage turns and `/compact` all pass the conversation's user. The bug this closes is latent: setup maps every identity to the one seeded user, so installs render the same prompt. A second user, as the designed `mapped` and `create` identity modes would create, sees their own blocks rather than the first user's. A PGlite test with two users pins the loader to the user it is given, and each caller's unit test pins that the blocks loaded for the conversation's user reach `assemble`.
