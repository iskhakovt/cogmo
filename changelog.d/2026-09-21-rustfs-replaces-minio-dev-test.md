**Dev, integration and e2e run RustFS 1.0.0 as the S3 stand-in.** `dev/containers.ts` exports `rustfs()` in place of `minio()`, pinned by digest to `mirror.gcr.io/rustfs/rustfs:1.0.0`, the first stable RustFS release (Apache-2.0), so a re-pushed tag cannot move dev and tests to a different build. The container is configured through RustFS's own interface rather than its MinIO compatibility shims: `RUSTFS_ACCESS_KEY` / `RUSTFS_SECRET_KEY` for the root credentials, the image's default `/data` volume, and a wait on `/health/ready`, the path RustFS's Helm chart uses as its readiness probe. The network alias is `rustfs`, so e2e reaches it at `http://rustfs:9000`.

The credentials are exported as `S3_TEST_ACCESS_KEY` / `S3_TEST_SECRET_KEY`, the same shape as `HINDSIGHT_TEST_API_KEY`, and `dev-infra.ts`, `integration-setup.ts`, `e2e-setup.ts` and `ensureFilesBucket` all read them from there. `pipeline.integration.test.ts` takes its S3 credentials from the env `integration-setup.ts` provides and fails loudly without them.

Production is unaffected: `S3_ENDPOINT` points at a real bucket there, and the `@aws-sdk/client-s3` call sites are unchanged. Every S3 operation the app issues was checked against RustFS 1.0.0 and the Chainguard MinIO image side by side, with identical results on both: CreateBucket twice, HeadBucket present and absent, Put and Get of text and a 70 KB binary with content type and `LastModified`, HeadObject and GetObject on a missing key (raising the SDK's `NotFound` and `NoSuchKey`, which `files.ts` and `attachment-store.ts` branch on), ListObjectsV2 with and without a prefix, a wrong secret rejected with `SignatureDoesNotMatch`, and objects surviving a container restart, as dev's `withReuse` needs. Both images were ready in about 1.3 s. RustFS also rejects its own default `rustfsadmin` credentials once `RUSTFS_*` are set.
