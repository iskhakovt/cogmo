MCP orchestrator wiring + `/mcp` admin commands (Phase A, PR 3 of 3). End-to-end: a user can now `/mcp add github <json>` → `/mcp approve github` → `/mcp approve github <tool>`, and the next conversation turn sees the MCP tool surface alongside built-ins and skills. New `composeTurnTools({builtIns, skillTools, mcpTools, toolSetGlobs})` in `src/skills/skill-tool-builder.ts` is the per-turn merge: `compileToolMatchers(toolSetGlobs)` filters every source, then the existing built-ins-win collision rule applies (rug-pull defense), then MCP tools layer on top (their `mcp__<server>__<tool>` prefix means structural collisions are impossible but the check is in place anyway). Empty `toolSetGlobs` = chat-only profile (zero tools); `["*"]` = all tools (matches picomatch's any-segment semantic). `handle-message.ts` now calls `mcpRegistry.resolveTools({toolGlobs: profile.toolSet})` per turn and passes the merged registry to `runStreamingAgentLoop`. Profile filtering is universal — every source is gated by `toolSet` globs — so `DEFAULT_TOOL_SET` in `src/setup/seed.ts` and `defaultToolSetFor` in `profile-dialog.ts` flip to `["*"]` to preserve historical "all tools surface" behaviour for unmodified profiles. New `Transport.mcp` namespace (`addServer`/`removeServer`/`listServers`/`approveServer`/`approveTool`/`rejectTool`) — every method identity-checked via `transportStore.resolveUser`, returns `mcp_disabled` when bootstrap didn't wire an `McpRegistry`, validates the config blob via `McpServerConfigSchema.safeParse` and returns structured `mcp_invalid_config` instead of throwing. Six new `TransportError` codes: `mcp_disabled`, `mcp_server_not_found`, `mcp_server_name_taken`, `mcp_invalid_config`, `mcp_tool_not_found`, `mcp_connection_failed`. New `/mcp` Telegram command (`src/transport/adapters/telegram/commands.ts → handleMcp`) with subcommands: `list` (renders `<name> [transport] — <status>, <approved>/<total> tools approved`), `pending` (filters to servers with unapproved state), `add <name> <json>` (parses trailing JSON config), `remove <name>` / `rm <name>` (resolves name → id), `approve <name>` (server-level connect-and-pin), `approve <name> <tool>` (per-tool flip), `reject <name> <tool>`. Wired into the bot via `bot.command("mcp", ...)`. New env vars: `MCP_TOOL_BUDGET` (default 25), `MCP_CALL_TIMEOUT_MS` (default 30_000), `MCP_IDLE_EVICTION_MS` (default 600_000), `MCP_EVICTION_INTERVAL_MS` (default 60_000). Bootstrap (`src/index.ts`) constructs a single shared `McpRegistryImpl` ahead of `startChannels` so both the orchestrator's per-turn `resolveTools` and every channel's Transport admin operations route through the same connection pool — duplicate registries would each spawn their own subprocess on first use. `main.ts` calls `mcpRegistry.stop()` in the shutdown `finally` after closing adapters and before sandbox shutdown. New tests: 7 `composeTurnTools` cases (empty-globs = no tools, `*` surfaces everything, exact-name back-compat, server glob filtering, mixed exact + glob across native/MCP, built-ins-win preserved across the merged list, no input mutation), 3 `handle-message` regression tests (resolveTools called with profile.toolSet, MCP tool surfaces in the merged registry alongside a real built-in, empty toolSet = empty registry — uses real `ToolRegistry` not `mockToolRegistry` because the latter's stubbed `register/snapshot` don't round-trip), 11 `/mcp` command tests (usage, empty list, populated list rendering, JSON parse, invalid JSON, server-level approve, per-tool approve, reject argument validation, remove resolves name → id, pending filtering, mcp_disabled friendly message). 1966 unit tests + integration tests pass; typecheck + biome clean. Phase A is now end-to-end usable.
