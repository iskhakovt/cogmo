Skill cron dispatch — manifests with `triggers: [cron]` + `schedule:` now actually fire.

Previously the `schedule` column on `skills` was populated by every `register` / `approve` / `rollback` path (and validated by the manifest schema) but nothing consumed it: no ticker scanned the table, no event was emitted, no handler called `runner.invoke` from a cron source. A skill declaring `schedule: "0 9 * * *"` parsed, deployed, and then sat silent forever.

Wired the missing dispatch path as a parallel Inngest cron, deliberately separate from the agent-scheduled-prompt machinery (`scheduled-task-ticker` / `agent/scheduled-task.fire` / `dispatch-fire`). The two cron systems share a wakeup mechanism and nothing else — agent prompts are user-scoped and rotate onto a synthetic inbound; skills are host-scoped and dispatch via `runner.invoke`. Co-owning a table across modules would have forced sync writes on every skill-lifecycle transition (`register` / `approve` / `denyDeploy` / `rollback` / `/enable` / `/disable` / `deregister`) and broken the CLAUDE.md store-pattern boundary.

Schema: two new columns on `skills` — `next_run_at TIMESTAMPTZ` and `last_fired_at TIMESTAMPTZ`. Partial index `idx_skills_due ON (next_run_at) WHERE schedule IS NOT NULL AND disabled = false` keeps the ticker's lock query to the b-tree subset that can actually fire. CHECK constraint `chk_skills_next_run_at_iff_schedule` enforces `(schedule IS NULL) = (next_run_at IS NULL)` at the DB boundary; the store layer asserts the same invariant pre-write to surface mismatches as a TypeError instead of an opaque Postgres error. `register` / `approve` / `rollback` now compute `next_run_at` via `computeNextRun(schedule, env.USER_TIMEZONE, now())` whenever the manifest sets a schedule, using the shared helper from `src/agent/scheduling/cron.ts`.

Ticker (`createSkillCronTicker`, `src/skills/cron-ticker.ts`): 1-min cron, `retries: 0` with cron-as-recovery, `concurrency: { limit: 1 }`, FOR UPDATE SKIP LOCKED on the partial index, per-row event id `${skillId}:${scheduledFor}` for Inngest event-bus dedup across retries. Skip-ahead policy — a row whose `next_run_at` is days in the past fires once with that stale timestamp and then advances to the first occurrence after `now()`. No `catchup_missed` knob; skills don't have the user-facing lateness UX that justified one for scheduled prompts.

Fire handler (`createSkillCronFireHandler`, `src/skills/cron-fire-handler.ts`): subscribes to `skills/cron.fire`, calls `runner.invoke({ name, inputs: {}, trigger: "cron" })`. Per-skill `concurrency: { limit: 1, key: "event.data.skillId" }` keeps two fires for the same skill from racing through the warm pool. Three pre-invocation branches translate `runner.invoke` exceptions into non-retrying skipped results: `skill_not_found` (deregistered between tick and fire), `skill_disabled` (disabled between tick and fire), `invalid_inputs` (manifest declared `required` inputs incompatible with the empty-inputs cron path — a deploy-time foot-gun). Anything else (sandbox transient, DB blip) propagates so Inngest's `retries: 2` budget catches it.

Test coverage: ticker store-tier unit tests (`src/skills/store/store.test.ts` — schedule/next_run_at invariant + `lockDueScheduledSkills` + `advanceSkillSchedule`), pure tick-body tests + Inngest wiring tests (`src/skills/cron-ticker.test.ts` — including replay safety on `lock-and-advance` and the `<skillId>:<scheduledFor>` idempotency key shape), and the fire-handler branch matrix (`src/skills/cron-fire-handler.test.ts` — success, skill-error, three skipped reasons, propagating-unknown-error, replay safety on `dispatch`). Existing skill tests that constructed `InsertSkillParams` / `ExecuteRegisterParams` / etc. were threaded with `scheduleNextRunAt: null` to match the tightened param shape.
