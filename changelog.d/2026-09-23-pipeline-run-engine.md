Pipelines can now run. Slice 1 compiled a free-text description into a versioned definition and stopped there — `activate_pipeline` told the user, honestly, that nothing would ever fire. `start_pipeline` now opens a run of an activated pipeline in the conversation the user asked from, and the engine walks it stage by stage to completion.

The engine is three short Inngest functions chained by events, with the `pipeline_runs` row as the only source of truth. `pipeline-stage-runner` enters a stage; `pipeline-stage-advance` records a finished stage's artifact and moves the cursor; `pipeline-gate-resolve` applies the user's decision at a gate. Nothing parks inside a function — a gate flips the run to `waiting_gate`, posts its prompt, and ends, so a week-long gate costs no in-flight state and survives any deploy. The design doc had proposed `step.waitForEvent` for short gates, on the stated grounds that coding delegation's plan approval works that way; it does not, and `waitForEvent` appears nowhere in the codebase. The doc is corrected.

**A stage is a conversation, not a function call.** The runner persists the stage's instructions and its predecessors' artifacts as a synthetic inbound — the `source = 'pipeline'` sibling of a scheduled fire — and ends. `handle-message` runs the turn with everything it already has: streaming, delivery, voice, history, compaction. The stage stays open across as many turns as the work needs, which is what makes the design doc's own worked example ("gather context — chat with you until I have enough") expressible at all; a stage bounded by one turn could never ask the user a question.

A stage therefore ends when the model says so, by calling `complete_stage` with the declared artifact. The tool is built per turn from the pinned definition, so its schema *is* the stage's declared output: `text` takes the text, `json` is validated against the compiler-emitted JSON Schema with violations handed back for the model to correct, a stage declaring no output takes a summary and stores nothing. It is the stage's only exit, and the only pipeline tool a stage ever gets — `define_pipeline`, `activate_pipeline` and `start_pipeline` are denied inside a run whatever its allowlist says.

Per-stage tool allowlists resolve at turn-build time rather than only at compile time. The profile's toolset, the installed skills and the approved MCP tools all move between compiling a definition and running it, so a stage narrows the tools that were actually composed for that turn, never widens them. A stage declaring no `tools` inherits the profile's set; one whose globs match nothing keeps `complete_stage` alone — it can finish, it just cannot act.

Gates are resolved by the user and nobody else. An Approve / Revise / Cancel inline keyboard on Telegram, `/gate approve | revise [feedback] | cancel` everywhere else, both through one identity-checked `Transport.pipelines.resolveGate`. No model sits between what the user decided and the transition. Revise sends the run back to the stage before the gate carrying the feedback as its note, at the next iteration — editing the remaining pipeline mid-run would mutate a pinned version, which is what pinning exists to prevent.

The run's cursor is `(current_stage, iteration)` and every function re-reads it before acting, so a redelivery, a superseded revise, or a decision that raced a cancellation is a no-op rather than a second entry into a stage. `iteration` is monotonic: forward moves carry it unchanged, backward moves increment it, which keeps each entry's idempotency keys distinct — including the synthetic inbound's, so a revised stage re-posts instead of silently reusing the first pass's row. One live run per conversation is a partial unique index, not a convention: a run supervises its conversation's turns, and two cursors over one thread is not a state the engine can hold.

Slice 2 is linear pipelines. A definition carrying a loop, a `wait` stage, or a `plan`/`pr_metadata` artifact is refused at run start with a specific reason rather than run as something it isn't. Gate timeouts are stored and previewed but not yet fired — that arrives with slice 3's ticker.

One thing this surfaced elsewhere: `handle-message` decided delivery routing by asking whether the batch was scheduled, and a pipeline stage's inbound has no originating session either. It now broadcasts for any synthetic source. The scheduled-fire guard that refuses a mixed batch was narrowed to what it actually protects — a fire must not share a turn with user input — since a stage's inbound legitimately can land inside an open debounce window.

An xhigh review of the branch turned up two bugs worth naming, both in the "this only bites on a retry" family. `complete_stage` compiled its stage's JSON Schema on a process-wide Ajv instance; Ajv keys its cache by object identity and the schema is deserialized fresh from the pinned definition every turn, so a schema carrying `$id` threw `already exists` on its second compile — killing the turn from the bare body of `handle-message` — and every other schema leaked a compiled validator per turn. Each stage tool now compiles on its own instance. And `start_pipeline`, which runs in a durable step, committed the run row and then emitted the first `stage.due`; a retry landing between the two found its own run via the one-live-run-per-conversation lookup and reported the conversation busy, leaving a run nothing would ever enter. It now recognises an untouched run of the same pinned version on its first stage as its own committed work and resumes at the emit.

The same review found the pipeline-authoring tools coming back at a gate — the denial was wired into the agentic-stage path only, so a user chatting while a gate waited on them had `define_pipeline` available inside a live run. Denial now applies to every turn inside a run. Smaller ones alongside: `/gateway …` no longer parses as a malformed `/gate` command on the Direct channel and the channel now answers a rejected gate command instead of going silent; a `json` stage output rooted at an array or a scalar is refused when the definition compiles rather than producing a stage that can be entered but never completed; a revise that lands on a gate carries its feedback into that gate's prompt instead of dropping it; and a revise with no earlier stage to return to re-requests the keyboard the channel already tore down.
