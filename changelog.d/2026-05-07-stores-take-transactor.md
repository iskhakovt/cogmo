### Stores take a `Transactor` instead of a full `Database`

Every Drizzle store implementation in the repo (`AgentStore`, `TransportStore`, `SandboxStore`, `CodingStore`, `SkillStore`, `McpStore`, `SecretsStore`) used to hold a private `Database` field and wrap every operation in `this.#db.transaction(async (tx) => { ... })`. The pattern was unanimous — no store ever called any other method on `#db` — but the interface was wider than the actual use: any store could in principle reach for `this.#db.select(...)` and slip a non-transactional read past review. The project rule "all DB operations use transactions" was enforced by discipline, not by the type system.

`src/db/index.ts` now exports a `Transactor` type — `<T>(cb: (tx: Transaction) => Promise<T>) => Promise<T>` — together with a `transactor(db)` adapter that closes over a `Database` and exposes only that one capability. Each store's constructor was changed from `db: Database` to `runInTx: Transactor`, and every `this.#db.transaction(cb)` body became `this.#runInTx(cb)`. The store has nothing else to call. Non-transactional access is now unrepresentable rather than merely discouraged, and a future "but I just need one quick read outside a transaction" temptation has nowhere to land.

Production wiring centralises one `const tx = transactor(db)` per process — `src/index.ts`, `src/seed.ts`, `src/setup/index.ts`, plus `src/setup/wizard.ts` for the wizard subprocess — and threads `tx` into every store construction site. The integration paths that build their own `drizzle()` instance inline (`admin-store.integration.test.ts`, `cross-provider.integration.test.ts`, `skills/runner.integration.test.ts`) wrap with `transactor(...)` at the call site.

`createTestDatabase()` in `src/test/pglite.ts` now returns `{ db, tx, close }` so PGlite-backed unit tests destructure `tx` once and pass it everywhere. `db` stays exposed for direct setup (`truncateAll`, raw `db.execute(sql\`…\`)`), since stores aren't the only thing tests need a database for. 23 store-test files were updated mechanically — add `Transactor` to the `db/index.js` import, add `let tx: Transactor;` to the var declarations, swap each `new DrizzleXStore(db)` for `new DrizzleXStore(tx)`. Three integration tests that don't use the PGlite helper were edited individually. The whole thing was a bulk-mechanical change with no logic moved or rewritten.

The naming went `RunInTransaction` → `Transactor` mid-flight — the helper was already called `transactor()`, so the type alias matches it. `Transactor` is a noun (good for a type), reads naturally at the construction site (`new DrizzleAgentStore(transactor(db))`), and the symmetric pair (`Transactor` type + `transactor(db)` factory) is easy to remember. `Store` was rejected — these things are the *dependency* of stores, not stores themselves; calling them stores would have conflated the two roles in code that already has named `Store` interfaces all over it.

No behavioural change. ~130 sites touched across 7 store impls and ~30 wiring locations; 2284 unit tests still pass; typecheck and lint clean for the modified files.

A future extension this pattern enables (not done here): cross-store transactions. The orchestrator currently calls `transportStore.getActiveChannelTypes(convId)` then passes the result into `agentStore.getActiveRules(...)` — two separate transactions. With the `Transactor` interface in place, a future "give me a function that runs both inside one tx" would slot in cleanly without restructuring the stores.
