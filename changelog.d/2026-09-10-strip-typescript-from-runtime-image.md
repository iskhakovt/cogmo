**The runtime image no longer ships a TypeScript compiler.** `.pnpmfile.mjs` drops the optional `typescript` peer at resolution time, and `@inngest/ai` moves to 0.1.8, which declares no dependencies. Together they take `typescript@5.9.3`, `typescript@7.0.2` and `@typescript/typescript-linux-x64@7.0.2` out of the production tree: `node_modules` in the image goes 450 MB → 394 MB and the image itself 199 MB → 185 MB.

Two separate routes put it there. `inngest` and `@t3-oss/env-core` declare `typescript` as an *optional* peer, and pnpm materialises optional peers regardless (pnpm/pnpm#11155) — `pnpm deploy --prod` then follows the edge. `@inngest/ai@0.1.7` took a blunter route and listed `typescript` under plain `dependencies`. The hook addresses the first; the version bump addresses the second, since 0.1.8 satisfies the `^0.1.3` that `inngest` asks for.

The hook keys on the peer being marked optional rather than on a list of dependent packages, so a new dependency declaring the same peer is covered without editing the file. Optional is the package's own assertion that it runs without the peer, and nothing in the production tree imports `typescript` outside type positions — a grep for `require("typescript")` / `from "typescript"` across every `.js`, `.mjs` and `.cjs` in the deployed tree returns nothing.

This is the bulk of the runtime image's Trivy findings. `@typescript/typescript-linux-x64` is the Go-built `tsc`, and Go stdlib CVEs compiled into that binary accounted for ten HIGH and one MEDIUM. A scan of the image before and after resolves those eleven and introduces none.

`.pnpmfile.mjs` has to reach the Docker build context, so it joins the root manifests in both the first `COPY` and the `.dockerignore` allowlist. The lockfile records a `pnpmfileChecksum`, which means a build that lost the file would fail its frozen install rather than resolve differently — the same loud-failure property the `patches/` note in `.dockerignore` describes.
