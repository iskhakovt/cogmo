**Pipeline stage turns and chat turns on a run's conversation run one at a time.** `handle-message` and `pipeline-stage-runner` share `conversationTurnConcurrency`, a limit of 1 on an env-scoped Inngest key per conversation, and `pipeline/stage.due` carries the run's `conversationId` to key on. A message sent into the run conversation while a stage turn is mid-flight waits for it instead of running a concurrent chat turn whose transcript interleaves with the stage's, and a stage due while a chat turn is in flight waits for that turn. Inngest counts executing steps rather than runs and orders them best-effort by run age: a run parked in a sleep or event wait frees the slot and, once woken, lets a younger turn in flight finish, while a step retried after an error can run between two steps of a younger turn. The field is optional in the schema, since the SDK validates a run's trigger event on every invocation: a stage sent or mid-turn across this deploy still runs instead of failing validation, though it isn't guaranteed to queue with chat turns. Both functions use the one constant because Inngest shares an env-scoped queue only between identical key expressions, not between expressions that evaluate to the same value. An integration test holds a stage's model call, sends a chat message into the run conversation, and asserts the chat turn reaches the model only after the stage call ends.
