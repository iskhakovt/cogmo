**A late reply now stops before it streams.** Each `llm-iter<N>` step of `handle-message` first asks `isTurnSuperseded`, before it calls the provider. That use case asks the persist check's two questions in one transaction, over rows newer than the reply admission found: has another run of the batch already replied on the turn's cursor (`TranscriptStore.isCursorAnswered`, new), and has a later turn row re-batched the cursor (`isCursorRebatched`)? If either holds, the step stores `{ kind: "superseded" }` and the loop stops without calling the provider or emitting anything. `finish-stream` closes the stream as finished, and the run ends `skipped: superseded` without `degraded-reply`, `persist-new-messages`, delivery or announcements. Until now, `persist-new-messages` refused such a reply only after it had reached the user. When the covering turn then failed for good, the user had the late reply, a failure notice, and the same words answered again by the next turn. Remaining residuals are in design/crash-recovery.md → Late replies: an iteration that started before the covering row committed still streams, and output from earlier iterations stays on screen with no transcript row.
