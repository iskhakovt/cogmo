Per-skill virtualenvs are now keyed by both the lockfile hash AND the runtime's Python ABI. The path becomes `/skill-venvs/<lockfile_hash>-py<major>.<minor>/` (e.g. `...-py3.14/`); previously just `/skill-venvs/<lockfile_hash>/`. Closes the wedge that the next `cogmo-skills` image bump changing Python minor would have triggered: stale venv at `<hash>/lib/python3.14/...` while the new supervisor looked for `lib/python3.15/...` -> `RuntimeError: skill_venv has no site-packages`. The populate script and supervisor both compute the ABI from their own `sys.version_info` (same image, same Python), so they agree by construction; the host doesn't need to know the image's ABI. The `task_invoke` protocol now carries `lockfileHash` instead of `skillVenv` (full path), since the supervisor constructs the venv path on its side. The supervisor independently validates `lockfileHash` against `^[0-9a-f]{64}$` so a malformed value on the wire can't compose a `..`-escape via `os.path.join`. The daily reaper computes its own ABI, builds the expected reachable set as `<hash>-py<CURRENT_ABI>` per row, and sweeps anything else that ages past the 7-day grace -- including stale ABI variants after an image bump and legacy bare-hash dirs from before this PR.

**Migration on existing deployments.** First invoke of each dep-locked skill after this PR merges pays a one-time re-populate cost (single-digit seconds) because the supervisor now looks for `<hash>-py3.14/` and the existing `<hash>/` no longer matches. The legacy `<hash>/` dirs orphan and are swept by the reaper after the 7-day grace window. No operator action required; first-invoke latency normalises on the second invoke.
