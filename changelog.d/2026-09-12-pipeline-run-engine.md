**User-defined pipelines run.** A compiled, activated pipeline with a `command` trigger now executes stage by stage: `start_pipeline` opens the run, `agentic` stages run as agent turns, and `gate` stages stop for the user's Approve / Cancel on Telegram. Definitions that use features the engine can't run yet — loops, `wait` stages, cron or event triggers, `plan` / `pr_metadata` artifacts — still compile, preview and activate; `start_pipeline` refuses them and names what blocks the run.

**Starting a run.** The model calls `start_pipeline(name)` when the user asks — by the trigger phrase or in their own words, so `trigger.phrase` is prose the model matches rather than a literal matcher. The run pins the active definition version, gets a conversation of its own, and the user's reachable channel sessions are routed onto it, the same rotation a scheduled fire performs. A pipeline with gates additionally needs a reachable channel whose adapter posts gate keyboards — `AdapterModule.pipelineGates`, set on Telegram — so a web-only user isn't started into checkpoints nobody can answer. The first `pipeline/stage.due` carries the starting chat conversation, and the first stage waits up to 30s for that turn's `response/ready` so it doesn't stream into the chat while the "run started" reply is still streaming. The tool is durable and keyed: `pipeline_runs.idempotency_key` carries the call's key, and a retry looks the run up before anything else — before the active-version lookup, since the pipeline may have been re-versioned or deactivated in between — and resumes it against its pinned definition, re-sending the first stage under its bus-dedup id.

**One short function per stage.** `pipeline-stage-runner` executes exactly the stage named by `pipeline/stage.due { runId, stageId, iteration }` and hands off by event. Every branch keys on the run snapshot memoized by its `load-run` step, and a delivery whose cursor no longer matches the run is skipped. The artifact and the cursor move commit in one step; the next `pipeline/stage.due` is emitted in a separate one, so a retry after the commit replays only the emit.

**Agentic stages** are agent turns built from the primitives `handle-message` composes — history load, `composeTurnTools`, `createService`, `compactMessages` with durable summaries, `runStreamingAgentLoop`, `insertMessages` — under stage policy: no debounce, batching, cooldown or voice. The stage's prose plus earlier artifacts become the user message, persisted as a `source='pipeline'` inbound keyed `pipeline:<runId>:<stageId>:<iteration>`; its id is the messages' cursor and the loop's `turnKey`. Those rows stay out of the chat pipeline's cursor — `getUnbatchedInbound` skips pipeline inbounds and `getLastAssistantMessage` skips assistant rows cursored on one — so a chat message sent around a stage is neither marked answered by the stage's reply nor batched together with its prompt. The stage allowlist narrows the profile's composed tools and can never widen them, and the four pipeline tools are always dropped — a stage's `Service` carries no `pipelines` namespace at all. Output streams by broadcast to every session on the run conversation. `text` artifacts are the final reply; `json` artifacts come from one tools-free call with the compiler's JSON Schema in the prompt, checked with ajv (a fresh instance per extraction, so a schema's `$id` never collides) and retried once with the errors fed back. The schema deliberately isn't sent as provider structured output: OpenAI-compatible providers enforce strict mode, which rejects ordinary schemas with optional properties. A degraded loop or an artifact that still fails its schema fails the run with the reason; a stage that exhausts its retries fails the run from `onFailure`.

**Gates park in the database.** A gate stage sets `waiting_gate` and emits `pipeline/gate.pending`. The Telegram adapter posts the keyboard, whose buttons carry the run id plus an 8-hex token of the gate key `${runId}:${stageId}:${iteration}` — a button left over from an earlier gate is refused rather than applied to the gate the run is parked on now. `pipeline-gate-waiter` sleeps out the timeout — one sleep per reminder, then `proceed` or `abort`. Taps and timeouts both emit `pipeline/gate.resolved`, deliberately without a dedup id, and `pipeline-gate-resolver` applies it in one step that opens with the conditional `waiting_gate → running` flip under a row lock: exactly one resolution wins, and the loser reads `stale` instead of cancelling a run the winner advanced. A tap's keyboard says the decision was *sent*, and a losing tap is told it wasn't applied. The waiter is cancelled by `pipeline/gate.settled`, which the resolver emits only after its step commits, so a tap whose resolution fails leaves the timeout armed and the user is told; a timeout that can't be applied fails the run. Only the waiter stays in flight across a deploy. `transport.pipelines.resolveGate` identifies the tapper before looking the run up, then checks them against the owner of the run's pinned definition. Decimal durations (`"4.1m"`) resolve to whole milliseconds and read back as written.

**Schema.** One migration: `pipeline_runs.idempotency_key` (plain `UNIQUE`, nulls distinct), a `pipeline` value on `inbound_message_source`, `inbound_messages.scheduled_fire_key` renamed to `idempotency_key` (with its partial unique index) now that pipeline stages store their keys there too, and the inbound CHECK rewritten as `source = 'user'` (session, no key) versus `source <> 'user'` (no session, key). Phrasing the system-source arm as `<> 'user'` rather than naming each source keeps the new enum value out of the constraint, so adding it and rewriting the CHECK share one transaction — Postgres refuses to use a freshly added enum value before it commits — and a future system source needs no constraint change. Three new `TransportError` codes (`pipelines_disabled`, `pipeline_run_not_found`, `pipeline_gate_not_pending`) are mirrored in `packages/contracts` under its parity guard.

`design/pipelines.md` moves the Execution Model and a new run-start section to `[confirmed]`, and drops its claim that coding delegation holds a `step.waitForEvent` open for plan approval: it parks the task at `awaiting_approval` and resumes in a separate function, which is the precedent the gate design follows. PROGRESS Phase 2's scheduled-tasks items, shipped some time ago, are ticked with wording corrected to what is in the code. Filed rather than shipped: stage turns and chat turns on the run conversation don't serialize against each other; a gate resolved by timeout leaves its (now inert) buttons on screen; stage batch delivery carries text but no generated attachments; and there is no surface to list or cancel an in-flight run. Revise at a gate folds into slice 3, since re-running the prior stage with feedback is a back-edge. The stage runner and gate turn share their in-turn retry policy (`createTurnStepRunner`) and scoped-`Service` assembly (`buildTurnService`) with `handle-message` rather than copying them. Every piece has unit coverage, including both functions' failure handlers; nothing yet exercises a run end to end against a real Inngest, which is the integration-tier gap PROGRESS Phase 6 already tracks.
