Memory writes flow through Observer-only classification — `memory_retain` no longer writes to Hindsight directly. New `pending_memories` staging table (migration `0021_purple_shockwave.sql`, with the `pending_memory_source` enum) holds each live retain until the next `conversation/idle`; Observer's new `drain-pending-memories` step classifies each row through `chatTyped()` and retains it via `retainBatch`. Single classification path means the live retain footgun ("agent stamps a coarse default that may be wrong") simply cannot exist — the same prompt assigns tags whether the fact came from a transcript or from a tool call.

`pending_memories` is user-scoped (FK to `users`, no `conversation_id`): `/reset` doesn't destroy pending rows, and any subsequent `conversation/idle` for the user drains them. Three columns of state — `content`, optional `context`, and `source` (`live_retain` | `migration`) — plus the standard `id` / `created_at`.

Extraction prompt now emits three independent tag axes per fact:

- `network:*` — world / bank / opinion / observation (unchanged).
- `compartment:*` — personal / work / health / financial / technical. Domain isolation, so a profile scoped to "work" never sees a personal-life fact.
- `trust:*` — first-party (default for anything sensitive) / any (only obviously public facts).

Service surface gains `memory.stageRetain(content, opts?)`; `createService` takes a sixth positional `stageRetain` closure that handle-message wires to `agentStore.stagePendingMemory({ userId, source: "live_retain", ... })`. The MemoryProvider interface stays untouched — staging is a Service-level concern backed by the agent store, since Hindsight has nothing to do with it.

Existing memories migrate via `scripts/migrate-memories.ts` (one-shot CLI: `pnpm tsx scripts/migrate-memories.ts <bankId>`). Sequence: paginate `listMemories` to read the bank → write JSON backup to `.dev/memory-backups/<bankId>-<iso>.json` → bulk-stage every row into `pending_memories` with `source: "migration"` (single Drizzle `.values([...])` insert) → `clearBankMemories` to wipe untagged rows. Backup write must succeed before any destructive step; if it throws, Hindsight stays intact. Drain happens organically on the next conversation idle through the same classifier prompt. The script refuses to run if the `pending_memories` table is missing — guards against running it before `pnpm db:migrate`.

Why a script, not a Drizzle migration: the data move calls Hindsight's HTTP API and depends on the Observer LLM pipeline being live to reclassify drained rows. Drizzle's runner is SQL-only, has no LLM access, and runs at deploy time before Hindsight may be reachable. The convention across TS migration tools (Drizzle, Knex, Prisma) is the same: SQL for schema, scripts for data backfills. The schema half lives in `0021_purple_shockwave.sql`; this script is the data half, run once per existing bank after the schema lands.

User-visible side effect: a live retain isn't searchable in a *different* conversation until the source conversation goes idle. Within the source conversation the fact is still in the LLM context; cross-conversation queries are usually well after idle, so the freshness gap is invisible in normal use. The "tell agent X, immediately open new chat, ask about X" workflow regresses by the conversation-idle delay (typically seconds).
