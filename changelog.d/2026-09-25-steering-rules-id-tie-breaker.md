Steering rules now sort by priority and then id, in both `getActiveRules` and `getCorrections`. Correction rules are all created at priority 100, and `upsertCorrection` bumps `observation_count` with an in-place update, which moves the row in the heap. With priority as the only sort key, Postgres returned tied rules in heap order, so an Observer update could reorder the `# Rules` section of the system prompt and invalidate the whole cached prompt with no rule having changed. A PGlite store test reproduces the reorder after an `upsertCorrection` and pins the id order. Groundwork for the prompt-caching plan in `design/prompt-caching.md`, whose system prompt snapshot relies on rules rendering in a stable order.
