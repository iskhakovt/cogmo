Steering rules sort by priority and then id, in both `getActiveRules` and `getCorrections`. Priorities are shared — every correction rule is created at 100, the seeded channel rules at 50 — and `upsertCorrection` promotes a rule with an in-place update that moves its row in the heap. Sorting by priority alone returns tied rules in heap order, so an Observer update could reorder the `# Rules` section and invalidate the cached system prompt with no rule changed. A PGlite store test creates and promotes two corrections through `upsertCorrection` and pins the id order. The prompt-caching design's system prompt snapshot (`design/prompt-caching.md`) relies on this order.
