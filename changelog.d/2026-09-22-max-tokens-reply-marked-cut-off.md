**Replies cut off at the output cap are marked, and a cut-off tool call never runs.** `classifyPostStream` has a `max_tokens` arm, so a turn that fills its output limit is never saved or delivered as if it were finished. What happens depends on where the cap landed:

- **A text reply** is kept. The model streamed it and it is the answer, but the loop appends `[Reply cut off: it reached the model's output limit.]` as a trailing text block and streams the same text straight after the partial. The live view, the transcript and the model's own history on the next turn all show where the reply stops, and the user can ask for the rest. If the cut lands inside a fenced code block, the notice closes the fence first, at the opener's indent so a block inside a list item stays closed in Telegram's renderer. Newlines the reply already ends with count toward the blank line before the notice. The push and its `agent.truncated` log line run in their own `truncation-notice-iter<N>` step, so an Inngest replay repeats neither. `AgentLoopResult.truncated` flags the turn.
- **A tool call** in a capped turn degrades the iteration (subtype `max_tokens`) before `executeToolCalls` runs. The call may be the block the cap cut off, and `jsonrepair` closes a cut-off argument object into one that still validates. Running it would act on truncated input, such as a half-written file or a clipped message. The iteration's streamed text and tool cards are retracted like any degrade, and the apology tells the user to ask for less or to split the task. When the adapter can tell the arguments were cut off rather than malformed — the failed call is the last block and the response stopped at the cap — it raises `ToolArgsCutOffError`. The loop then degrades straight away instead of paying for a non-streaming replay that would stop at the same cap.
- **No visible text** (the allowance went on reasoning) also degrades with subtype `max_tokens`. There is nothing to keep.

A pipeline stage whose reply was cut off fails instead of extracting an artifact from half a document. The reply is still persisted and delivered. A degraded stage turn retracts its dropped iteration's streamed output from the run's sessions before it fails, as chat does before its apology; `computeRetraction` moves to `agent/retraction.ts` so both orchestrators share it. `conversation/degraded` accepts the new subtype.

`extractText` in `llm/content.ts` replaces the hand-written copies of "join a message's text blocks" across the agent loop, repair, sub-agents, pipelines and transport, including the last `as { text: string }` cast in `chatTyped`.

There is no automatic "continue" repair. Current Claude models reject assistant prefill. A synthetic continuation turn would either put words in the user's mouth or, if dropped afterwards as the other repairs do, rewrite the prefix Anthropic binds thinking blocks to. And the cap the loop sends is already the model's resolved `maxOutputTokens`, so a retry re-bills the whole input and usually stops in the same place. The prefix-binding problem also affects the existing `empty_end_turn` repair and keep-tail compaction, so it is tracked in `todo.md`.

The non-streaming `runAgentLoop` has no production callers and no Class C classifier, so it is unchanged: it still runs every tool call it receives.

OpenAI-compatible providers report a context-window overrun and an output-cap stop with the same `finish_reason: "length"`, so an overrun there is treated as a cut-off reply. Telling them apart would need a signal the wire format doesn't carry: comparing `completion_tokens` against the requested cap misfires on providers that clamp the cap silently, and the resolved context window isn't reliable for self-hosted servers.
