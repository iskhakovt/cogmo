**Replies cut off at the output cap are marked, and a call the cap cut off is answered instead of run.** `classifyPostStream` has a `max_tokens` arm, so a turn that fills its output limit is never saved or delivered as if it were finished. Blocks are generated in order and the cap stops generation, so only the reply's last block can be incomplete — which is what decides the outcome:

- **Ends in text, no tool calls:** the text is the answer and stays. The loop appends `[Reply cut off: it reached the model's output limit.]` as a trailing text block, streams the same text after the partial, and sets `AgentLoopResult.truncated`. The user can ask for the rest.
- **Ends in a tool call:** that call is answered, not run. `jsonrepair` closes its cut-off arguments into an object that still validates, so running it would act on truncated input — a half-written file, a clipped message. It gets a synthetic `is_error` tool_result naming the cause and the way out ("split the work into smaller calls"), on the interception channel the volume-cluster trigger already uses, and the turn carries on with the model re-deciding. Earlier calls in the same iteration are whole and run normally. A second cut-off call exhausts the `max_tokens: 1` budget and degrades.
- **Ends in text or reasoning after complete calls:** the calls run. Their results give the model the room to finish the sentence.
- **No visible text:** degrade. The allowance went on reasoning and there is nothing to keep.

The notice sits one blank line below the reply, counting newlines it already ends with, and closes an open code fence at the opener's indent — an unindented closer ends a list item and opens a fresh block in Telegram's renderer, swallowing the marker. Its push runs in a `truncation-notice-iter<N>` step so an Inngest replay can't repeat it, with the `agent.truncated` log line after the push so it counts delivered notices.

When the arguments are mangled enough that the adapter can't rebuild the call, there is no block to answer. Both adapters now separate that case from a cut-off one — the failed call is the response's last and it stopped at the cap — and raise `ToolArgsCutOffError`, which degrades the turn instead of paying for a non-streaming replay that would stop at the same cap.

A pipeline stage whose reply was cut off fails rather than extracting an artifact from half a document; the reply is still persisted and delivered. A degraded stage turn also retracts its dropped iteration's streamed output before failing, as chat does before its apology — `computeRetraction` moves to `agent/retraction.ts` so both orchestrators share it. `conversation/degraded` accepts the new subtype.

Nothing re-requests a capped text reply. Current Claude models reject assistant prefill, and a synthetic continuation turn either puts words in the user's mouth or, dropped afterwards as the other repairs do, rewrites the prefix Anthropic binds thinking blocks to. The repair's tool_result has neither problem: it is a real turn in the transcript. That prefix-binding hazard also affects the existing `empty_end_turn` repair and keep-tail compaction, and is tracked in `todo.md`.

`extractText` in `llm/content.ts` replaces the hand-written copies of "join a message's text blocks" across the agent loop, repair, sub-agents, pipelines and transport, including the last `as { text: string }` cast in `chatTyped`.

Two limits stand. The non-streaming `runAgentLoop` has no production caller and no Class C classifier, so it still runs every tool call it receives. And OpenAI-compatible providers report a context-window overrun with the same `finish_reason: "length"` as an output-cap stop, so an overrun there is treated as a cut-off reply: comparing `completion_tokens` against the requested cap misfires on providers that clamp it silently, and the resolved context window isn't reliable for self-hosted servers.
