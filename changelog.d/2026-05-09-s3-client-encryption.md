New `S3_CLIENT_ENCRYPT=true` flag wraps the attachment store with client-side AES-256-GCM, so newly-stored objects are ciphertext. Off by default. The wrapper is a transparent decorator (`src/transport/encrypted-attachment-store.ts`) over the existing `AttachmentStore` interface — every consumer of attachments (image-tools, document-tools, Telegram inbound/outbound, integration tests) is unchanged. Object body layout is `[magic 4B: 0xC0 0x6C 0x6D 0x6F][version 2B BE][nonce 12B][ciphertext + GCM tag]`: 18 bytes of header, with magic and version separated so neither is overloaded. The 4-byte magic does the "is this a Cogmo-encrypted blob?" job — `0xC0` is an invalid UTF-8 lead byte (never a valid first byte of UTF-8 text) and combined with `lmo` doesn't collide with the magic of any common attachment format (JPEG `0xFF`, PNG `0x89`, GIF `0x47`, WebP `0x52`, PDF `0x25`, OGG `0x4F`). Collision probability for arbitrary plaintext is ~1 in 2³². Reads dispatch on the magic — encrypted blobs decrypt strictly, anything else returns raw bytes — so flipping the flag on a populated bucket is a no-op for old objects: pre-flag plaintext stays readable, new uploads are ciphertext, churn converges the bucket over time. No flush, no sweep script, no migration window. The 2-byte big-endian version field separates "is this encrypted?" from "what cipher format?" so future format changes (key rotation, AEAD swap) can roll forward without changing the magic predicate.

Key derivation reuses the secrets-at-rest pattern: `deriveMasterKey(parseMasterKey(env.COGMO_MASTER_KEY), "cogmo/s3-attachments/v1")`. The HKDF purpose string isolates the attachment key from the secrets-table key and from the future webhook-HMAC key — leaking one derived key never compromises the others. New binary `encryptBytes`/`decryptBytes` in `src/secrets/encryption.ts` skip the UTF-8 round-trip the existing string-typed `encrypt`/`decrypt` perform; PNGs and PDFs aren't UTF-8 and would mangle through `TextEncoder` / `TextDecoder`.

`Service.files` (the agent's text workspace bucket) is intentionally left in plaintext. Those objects are addressed by skill code at the S3-path level — encrypting them would force every skill invocation to round-trip bytes through Cogmo instead of letting Pyodide / sysbox workers fetch them directly via the SDK.

The wrapper also pins the inner-store media type to `application/octet-stream` on every encrypted upload, regardless of the caller's value. That neutralizes two metadata leaks the storage provider would otherwise see — the `Content-Type` header on the S3 object (would have been `image/jpeg` etc., advertising the original file type even though the body is opaque) and the file extension in the path (`mediaTypeToExt("application/octet-stream")` resolves to `.bin` thanks to a one-line addition to the existing extension table). Matches `rclone crypt`'s documented convention of `.bin` extensions on the underlying remote when name-encryption is off — same rationale, in their words: "prevents the cloud provider attempting to interpret file content." Consumers that need the original media type get it from persisted message metadata (`messages.content`, `inbound_messages.content`), never from the bucket — the neutralization is invisible above the `AttachmentStore` boundary.

The operational caveats from the original todo entry stand and are now captured in the env-var doc: rotating `COGMO_MASTER_KEY` still requires re-encrypting every existing attachment (the read fallback is plaintext-vs-magic, not multi-key), the bucket loses direct-browser-serve (a `<img src="r2-url">` would render ciphertext), and `aws s3 cp` / `rclone` / the R2 dashboard show opaque blobs labelled `.bin`. That's the trade-off operators opt into when they want Cloudflare-blind storage.

Test coverage: 38 wrapper tests (round-trip on arbitrary binary, header-layout assertions, random-nonce / wrong-key / tampered-cipher / tampered-nonce / tampered-version / missing-magic / too-short / unknown-version detection, plaintext-passthrough on JPEG/PNG/PDF/short/empty/near-miss-magic, magic-collision plaintext surfacing as caller-visible error, content-type pinning across image/audio/pdf inputs, empty-plaintext encrypt path, **golden fixture pinning the v1 wire format** so reordering magic bytes / flipping version endianness / shifting the nonce offset is caught at compile time of the test rather than at runtime in production), 10 helper tests for `mediaTypeToExt` (covers all `MIME_EXT` entries plus suffix / fallback / malformed-input branches), and 5 helper tests for `encryptBytes` / `decryptBytes`.

Library evaluation: there's no Node.js library in the ecosystem that does "AEAD a Buffer with a versioned, opaque-on-disk envelope" the way we want. Tink's TypeScript port was archived by Google in April 2024. age (typage) doesn't expose a raw-symmetric-key API — its built-in modes are X25519 recipients, scrypt-from-passphrase, and WebAuthn passkeys, none of which fit "we already have a 32-byte HKDF-derived key." JWE inflates by 33% via base64. Fernet uses AES-CBC + HMAC, not GCM. AWS S3 Encryption Client has no Node port and stores its envelope in S3 metadata headers (different convention from our self-contained-blob approach). At primitive level we're already on `@noble/ciphers` (audited, tree-shakeable, used elsewhere in the secrets module); at envelope level there's no fit, so the ~150 LOC of mechanical Buffer manipulation is the right scope.
