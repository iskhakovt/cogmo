New `S3_CLIENT_ENCRYPT=true` flag client-side AES-256-GCM-encrypts both **attachments** (image / audio / document bodies via `AttachmentStore`) and **workspace files** (`read_file` / `write_file` via `Service.files`). Off by default. The bucket sees only ciphertext bodies — useful when the bucket is provider-managed (Cloudflare R2, public-cloud S3) and the operator doesn't want the storage provider readable. Reads transparently fall back to plaintext when the magic prefix is absent, so flipping the flag on a populated bucket is a no-op for old objects: pre-flag plaintext stays readable, new uploads are ciphertext, churn converges the bucket over time. No flush, no sweep script, no migration window.

On-disk format `[magic 4B: 0xC0 0x6C 0x6D 0x6F][version 2B BE][nonce 12B][ciphertext + GCM tag]` — 18-byte header, self-contained blob. The 4-byte magic does the "is this Cogmo-encrypted?" check (`0xC0` is an invalid UTF-8 lead byte and doesn't collide with the magic of any common attachment format — JPEG `0xFF`, PNG `0x89`, GIF `0x47`, WebP `0x52`, PDF `0x25`, OGG `0x4F`; collision probability for arbitrary plaintext is ~1 in 2³²). The 2-byte big-endian version separates "is this encrypted?" from "what cipher format?" so future format changes (key rotation, AEAD swap) can roll forward without changing the magic predicate. Byte-level primitives (`encryptBuffer` / `decryptBuffer` / `isEncrypted`) live in `src/secrets/blob-envelope.ts` and are shared by both stores so the on-disk format and HKDF purpose string match — one master key covers everything in the bucket.

Two stores, two patterns. `AttachmentStore` gets the decorator pattern (`wrapAttachmentStoreWithEncryption`) — its `Buffer → Buffer` interface fits transparent wrapping. `Service.files` gets an optional encryption argument inside `createFileService` — its string-typed interface (`read(): Promise<string>`, `write(content: string)`) creates an impedance mismatch for a Buffer-only decorator, so two small branches inside `read`/`write` (encrypt UTF-8 bytes on write, decrypt-or-passthrough on read) beat duplicating ~50 LOC of S3 boilerplate in a parallel implementation. Both stores set `Content-Type: application/octet-stream` when encrypted; attachments additionally get neutralized file extensions (`.bin` via a one-line addition to `mediaTypeToExt`), matching `rclone crypt`'s documented convention of `.bin` on the underlying remote when name-encryption is off — same rationale, in their words: "prevents the cloud provider attempting to interpret file content." Consumers that need the original media type get it from persisted message metadata (`messages.content`, `inbound_messages.content`), never from the bucket.

Object keys (S3 paths) remain plaintext for both stores. Matches the [AWS S3 Encryption Client convention](https://docs.aws.amazon.com/amazon-s3-encryption-client/latest/developerguide/concepts.html): "the object key path itself is not encrypted by the S3 Encryption Client and remains visible to AWS and anyone with access to list S3 objects." For attachments this is irrelevant — paths are random UUIDs (`generated/<uuid>.bin`). For workspace files the trade-off is real and operator-visible: if you don't want file names visible to the storage provider, choose non-revealing names. Full path-name encryption like rclone crypt's standard mode is a much bigger change — it would break `list_files` semantics and the agent's mental model of addressing files by name; deferred until/if it's actually needed.

Key derivation reuses the secrets-at-rest pattern: `deriveMasterKey(parseMasterKey(env.COGMO_MASTER_KEY), "cogmo/s3-objects/v1")`. Purpose-isolated HKDF — leaking one derived key never compromises the others. The purpose string deliberately says "s3-objects" rather than "s3-attachments" because it covers both stores. New binary `encryptBytes`/`decryptBytes` in `src/secrets/encryption.ts` skip the UTF-8 round-trip the existing string-typed `encrypt`/`decrypt` perform; binary payloads aren't UTF-8 and would mangle through `TextEncoder` / `TextDecoder`.

Operational caveats are now in the env-var doc and `DEPLOYMENT.md`: rotating `COGMO_MASTER_KEY` requires re-encrypting every existing object (the read fallback is plaintext-vs-magic, not multi-key); the bucket loses direct-browser-serve (a `<img src="r2-url">` would render ciphertext); `aws s3 cp` / `rclone` / the R2 dashboard show opaque blobs; toggling the flag *off* with encrypted blobs leaves them unreadable to consumers (image decoders / `read_file` would crash on raw ciphertext).

Library evaluation: no Node.js library in the ecosystem does "AEAD a Buffer with a versioned, opaque-on-disk envelope" the way we want. Tink's TypeScript port was [archived by Google in April 2024](https://github.com/google/tink/issues/689). age ([typage](https://github.com/FiloSottile/typage)) doesn't expose a raw-symmetric-key API — its built-in modes are X25519 recipients, scrypt-from-passphrase, and WebAuthn passkeys, none of which fit "we already have a 32-byte HKDF-derived key." JWE inflates by 33% via base64. Fernet uses AES-CBC + HMAC, not GCM. AWS S3 Encryption Client has no Node port and stores its envelope in S3 metadata headers (different convention from our self-contained-blob approach). At primitive level we're already on `@noble/ciphers` (audited, tree-shakeable, used elsewhere in the secrets module); at envelope level there's no fit, so the ~150 LOC of mechanical Buffer manipulation is the right scope.
