New `S3_CLIENT_ENCRYPT=true` flag wraps the attachment store with client-side AES-256-GCM, so the underlying S3 / R2 / MinIO bucket only ever sees ciphertext. Off by default. The wrapper is a transparent decorator (`src/transport/encrypted-attachment-store.ts`) over the existing `AttachmentStore` interface — every consumer of attachments (image-tools, document-tools, Telegram inbound/outbound, integration tests) is unchanged. Object body layout is `[ver=0x01][nonce 12B][ciphertext + GCM tag]`: the version byte lets a future format change roll forward without a re-encryption migration, and the self-contained blob means no separate metadata table or R2-side header to stay in sync.

Key derivation reuses the secrets-at-rest pattern: `deriveMasterKey(parseMasterKey(env.COGMO_MASTER_KEY), "cogmo/s3-attachments/v1")`. The HKDF purpose string isolates the attachment key from the secrets-table key and from the future webhook-HMAC key — leaking one derived key never compromises the others. New binary `encryptBytes`/`decryptBytes` in `src/secrets/encryption.ts` skip the UTF-8 round-trip the existing string-typed `encrypt`/`decrypt` perform; PNGs and PDFs aren't UTF-8 and would mangle through `TextEncoder` / `TextDecoder`.

`Service.files` (the agent's text workspace bucket) is intentionally left in plaintext. Those objects are addressed by skill code at the S3-path level — encrypting them would force every skill invocation to round-trip bytes through Cogmo instead of letting Pyodide / sysbox workers fetch them directly via the SDK.

The operational caveats from the original todo entry stand and are now captured in the env-var doc: rotating `COGMO_MASTER_KEY` requires re-encrypting every attachment, the bucket loses direct-browser-serve (a `<img src="r2-url">` would render ciphertext), and `aws s3 cp` / `rclone` / the R2 dashboard show opaque blobs. That's the trade-off operators opt into when they want Cloudflare-blind storage.
