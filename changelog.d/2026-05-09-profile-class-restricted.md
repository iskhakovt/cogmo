Profile-class `restricted` flag for fail-closed recall (#198). Adds a `restricted` boolean to `profile_classes`; memories tagged with a restricted class are invisible to any profile that doesn't either explicitly opt the class into `memory_scope.profileClasses` or speak as the class itself. Default `false` keeps today's open-by-default behaviour for existing classes; flipping the flag is the single switch operators reach for when a class is sensitive (the canonical case: an `intimate` profile whose memories must not leak into an `assistant` profile that forgot to set `memory_scope`).

The Service composes a NOT leaf alongside the existing scope leaves: `{ not: { tags: ["profile_class:r1", …], match: "any" } }` over the set of restricted classes the profile hasn't opted into. `match: "any"` (not `any_strict`) — only memories carrying one of those tags are excluded; untagged legacy rows pass through. Implicit speaker auto-include keeps a restricted-speaker profile able to recall its own writes when no explicit scope is set, so an `intimate`-class profile with `memory_scope = null` reads everything *except* other restricted classes — the ergonomic default.

**Speaker auto-include is structural, not opt-in**: when `scope.profileClasses` *is* explicitly set, the Service still adds the profile's own class to the `any_strict` leaf so a profile always sees its own writes. Matches the convention in personal-data systems (email's "Sent" folder, Drive owner-implicit-read, PostgreSQL RLS's `owner = current_user` idiom). The `formatScope` rendering surfaces this — when speaker auto-include kicks in, the rendered classes line shows the speaker class with a trailing `(speaker)` annotation so the operator's view matches the effective filter, not just the stored config. Behaviour change for any pre-existing PR-#180 deployment that intentionally configured `scope.profileClasses` to exclude the speaker — the speaker class is now always visible to itself; if you need a write-only / no-self-recall pattern (auditor-style), express it via `profile.profileClass = null` (write untagged) instead of misconfiguring the scope.

Telegram surface: `/classes restrict <name>` / `/classes unrestrict <name>`, plus restricted-class markers in `/classes list` (`(restricted)` + a legend), `/profile list` (`[class=intimate*]`), and `/profile scope` / `/status` (`classes: intimate!` with `(! = restricted)` legend, mirroring the existing `* = custom` pattern from PR #194). `/classes rm` is independent of `restricted` — the FK-RESTRICT contract still gates deletion of in-use classes regardless of the flag, and forward-only-on-tags semantics still apply: marking a class restricted has no retroactive effect on already-tagged Hindsight memories.

Migration is a single `ALTER TABLE … ADD COLUMN restricted boolean NOT NULL DEFAULT false`. The `createService` signature gains two adjacent positional args (`speakerClass`, `restrictedClassNames`) right after `memoryScope`; the orchestrator loads the restricted-class list once per turn alongside the existing profile load. Today-fast-path is preserved — null scope + zero restricted classes still emits zero leaves and goes through the same `opts ?? {}` short-circuit.
