Skill run telemetry — `resource_usage` JSONB column on `skill_runs` capturing per-task wall-clock and peak memory.

Previously every `skill_runs` row carried only `status` / `output` / `error` / `created_at` / `finished_at`. The wall-clock duration was derivable but not stored; peak memory wasn't captured at all. Operators auditing skill cost or chasing OOM-prone manifests had no signal beyond "did the row error."

Schema: one new column on `skill_runs`. The JSONB-blob shape (rather than two flat columns) mirrors `coding_tasks.resource_usage` — one "what the runtime cost us" blob per row, extensible to `cpuSeconds` / `ioBytes` / `forkCount` later via Zod-schema additions instead of migrations. Tradeoff against indexability is fine at single-user scale; aggregate queries can `(resource_usage->>'wallClockMs')::int` when needed.

`SkillRunResourceUsageSchema` in `src/skills/types.ts` declares `{ wallClockMs: number, peakMemoryBytes: number | null }`. `wallClockMs` is always set — host-derived from `finishedAt - run.createdAt` at finalisation time, including timeouts and crashes (where `finishedAt = wall_clock_cap`). `peakMemoryBytes` is nullable for the cases where the runtime can't surface a reliable per-task value:

- **Tier 1 (Pyodide WASM)**: `null`. The Pyodide worker runs in a Node Worker thread, but `getrusage(RUSAGE_SELF)` reports process-wide peak RSS. Under concurrent workers (multiple skills firing through the same Cogmo process) the number is shared across all of them — useless as a per-skill signal. Revisit if Pyodide ever exposes a per-VM heap-size hook; until then null is honest.
- **Tier 2 (sysbox supervisor / Daytona)**: populated. Each task forks a fresh child from the supervisor; the child calls `resource.getrusage(resource.RUSAGE_SELF).ru_maxrss * 1024` (Linux `ru_maxrss` is in kilobytes) just before emitting `task_result` and includes it in a new optional `rusage` block on the protocol message.
- **Synthesised tier-2 results**: also `null`. The supervisor synthesises a `task_result` for wall-clock kills, SIGKILL, waitpid errors — none of those paths see the child's rusage. The wall-clock column still reflects the (typically capped) duration.

Protocol additions in `src/skills/protocol.ts`: `RuntimeRusageSchema` (optional `peakMemoryBytes`), threaded as an optional field onto both `TaskResultOk` and `TaskResultErr` variants. `RunOnWorkerResult` (tier-1 host return) and `InvokeResult` (tier-2 worker return) gain the same optional `rusage` field; the cast in `worker.ts` that previously truncated `TaskResult` to `{ ok, output, error }` was widened. Backward-compatible — old worker images that don't emit `rusage` produce a `null` `peakMemoryBytes` in the persisted row.

Store: `UpdateRunResultParams` gains a required `resourceUsage` field; `SkillRow` and the Drizzle writer thread it. Every existing test that calls `updateRunResult` was updated to pass a sentinel `resourceUsage` value — these are the three sites in `store.test.ts` that exercise the run-result write path. A negative-`wallClockMs` test asserts the Zod boundary rejects malformed blobs on write.

Test coverage: four new Python tests in `images/skills/tests/test_runner.py` (`TestRusage` covering ok + error branches), four new TS protocol tests in `src/skills/protocol.test.ts` (rusage on ok / err variants, optional absence for synthesised results, negative-bytes rejection), four new store-tier tests in `src/skills/store/store.test.ts` (`resource_usage round-trip`: null on insert, both fields persisted, null peak-memory on tier-1/timeout, Zod rejection on negative wall-clock), plus an assertion in the existing `invokes a tier-1 skill end-to-end (Pyodide load)` test that `resourceUsage.wallClockMs >= 0` and `peakMemoryBytes === null` for the tier-1 path. Full unit-tier passes (3899 tests).
