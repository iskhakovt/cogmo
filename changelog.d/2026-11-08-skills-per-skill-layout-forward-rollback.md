Each skill now lives in its own `skills/<name>/` directory on the skills repo's `main`, and a rollback is a forward commit (design/skills.md → Per-skill structure, Deploy lifecycle).

- The first boot of this release moves every deployed skill from the repo root to `skills/<name>/` in one layout commit under Cogmo's own identity (`Cogmo <skills@cogmo.invalid>`, `Cogmo-Layout: v1` trailer), recorded in the new `skills_repo_layout` table. A sha from before that commit still reads from the root, so live skills keep running at their recorded shas. If the table is empty and `main`'s merges bring in more than one candidate layout commit, none of them on its first-parent history, the boot fails naming them, and the operator records the right one by inserting its row.
- Register takes the skill from the branch's change: `main..tip` must touch only one skill's `SKILL.md`, `skill.py`, `requirements.lock` and `test_skill.py` in `skills/<name>/`, whose manifest names `<name>`. Skill files at the root, or a commit carrying Cogmo's identity or a `Cogmo-` trailer, are refused as `layout_violation`; another path or a second skill as `owned_paths`; a mismatched name as `skill_name_mismatch`.
- A rollback commits the target's files to `skills/<name>/` on top of `main` (`Cogmo-Restores` trailer), so `main` only fast-forwards, no other skill's deploy leaves `main`, and the mirror is a plain push. The deploy row records the target in the new `restores_git_sha`, and `enable` accepts a rolled-back skill whose target once went live.
- `cogmo serve` pushes `main` to the skills remote at boot, best-effort, so the layout commit reaches the remote a Daytona task branches from.
- Configuring the skills remote counts a `main` holding only the boot's empty layout commit as unborn, so `cogmo migrate-skills-remote` can still adopt an existing remote on a deployment that never deployed a skill; the adopted `main` is then moved in turn and pushed back.
- The coding agent's skills-repo convention now asks for `skills/<name>/`.
