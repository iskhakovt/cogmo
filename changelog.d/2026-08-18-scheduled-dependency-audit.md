A weekly workflow re-runs `pnpm audit --prod` and tracks the result in a single issue, restoring the ratchet that emptying `overrides:` gave up.

Dropping the seven security overrides was what the block's own comment prescribed — each had been superseded by a dependency bump that pulled the patched range in directly — but it traded a durable floor for a point-in-time measurement. An `overrides:` entry keeps ratcheting; a lockfile that happens to satisfy the same range does not. `@grpc/grpc-js` shows the shape of the risk: it resolves to exactly 1.14.4, the floor its override used to enforce, so a parent narrowing its range would re-resolve under a critical advisory with nothing to notice.

Scheduled rather than a PR gate, which is the whole design point. Auditing on `pull_request` would let a fresh advisory in any transitive dependency block every unrelated PR until someone fixed it — a merge-gate policy this repo doesn't want. Dependabot's `npm-security` group still opens PRs for advisories it can fix on its own; this covers what that misses, the advisory with no patched version yet or one whose fix needs a decision, by making it visible instead of silent.

The job opens one labelled issue and comments on it while the condition persists, then closes it on the first clean run, so an open issue means the production tree has an advisory now rather than that one was seen once. `--prod` scopes it to what ships. The report reaches the issue body through an environment variable rather than shell interpolation, and pnpm's exit code is the signal — 0 clean, non-zero found — so the step reads it instead of failing on it.
