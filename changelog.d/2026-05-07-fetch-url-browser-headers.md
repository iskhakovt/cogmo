### `fetch_url` looks like real Chrome and falls back to Tavily Extract

Bot filters on the no-reputation IP we run `fetch_url` from were rejecting page reads too often (403/429), even on plain public articles. Two changes ship together — header upgrade and a fallback path.

**Chrome-shaped headers.** The previous header set was a UA, `Accept`, and `Accept-Language` — enough to clear the cheapest filters but missing the User-Agent Client Hints and fetch-metadata that real Chrome ships on every navigation. The request now sends the canonical Chrome desktop navigation header set: `User-Agent` (Chrome 138, Linux x86_64), `sec-ch-ua` / `sec-ch-ua-mobile` / `sec-ch-ua-platform` (kept consistent with the UA — a UA/platform desync is itself a bot signal), the `Sec-Fetch-Site` / `Mode` / `User` / `Dest` quartet describing a top-level navigation from a typed URL, `Upgrade-Insecure-Requests`, an `Accept` value with the q-values and image-format list Chrome sends verbatim (the q-value order is part of the fingerprint), and `Accept-Encoding: gzip, deflate, br`. We skip `zstd` despite Chrome advertising it, since undici decode support is uneven across Node releases and a garbled body is worse than a missing header.

403 and 429 are now treated as retryable, and the second attempt switches to a same-origin `Referer` and `Sec-Fetch-Site: cross-site` — the "no-referer = bot" filters that send a 403 on the first hit usually let a refered retry through. The User-Agent stays pinned across attempts: UA churn during a single fetch is itself a flag, and we have no IP rotation to pair it with. 5xx is still retryable as before.

**Tavily Extract fallback.** When the direct fetch fails with a bot-block-shaped error (403/429 after the retry-with-Referer round, 5xx after retries, or a network-level timeout) the tool now falls back to `POST https://api.tavily.com/extract` with the same key already plumbed through for `web_search`. Permanent failures (404, 401, other non-retryable 4xx — flagged as `p-retry` `AbortError` inside `directFetch`) propagate as-is and never trigger the fallback, so we don't burn a credit relaying "page doesn't exist". When Tavily also fails, the surfaced error names both legs (`Direct fetch: …. Tavily fallback: …`) so a future debugger can tell whether the headers need more work or whether the site genuinely needs a real browser. The fallback is invisible to the agent — same tool, same return shape, just with a different fetcher behind it. Tavily Extract is cheap (1 credit per 5 successful extractions on `basic` depth, the mode we use), and it only fires when the cheap path failed, so the credit cost stays in the noise for normal use.

This still won't beat Cloudflare Turnstile or strict JA4 TLS-fingerprint blocks — those need a real browser or `curl-impersonate`, which is overkill for a one-shot read. A future follow-up could add a per-call cookie jar across the redirect chain (sites that 302-set a `__cf_bm` and require it on the redirected GET); that needs a runtime dep (`fetch-cookie` or `tough-cookie`), so it's deferred for discussion.

The `web-tools` test mock for `withRetry` also got upgraded from a single-shot passthrough to a no-delay retry loop that honours `AbortError`. New tests cover the Chrome header set on the first attempt, retry-on-403 with a `Referer`, retry-on-429, the Tavily fallback success path, the no-fallback-on-404 path (404 means "doesn't exist", not "blocked"), the no-fallback-when-key-missing path, and the both-failed combined-error path.
