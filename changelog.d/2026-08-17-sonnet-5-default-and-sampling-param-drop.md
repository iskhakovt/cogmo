The seeded default profile now targets `claude-sonnet-5` instead of `claude-sonnet-4-6`. Same tier, same 1M/64k limits already present in the bundled LiteLLM snapshot, and identical list pricing — but the bump exposed that the Anthropic adapter was written against the 4.6 request surface, so the model swap is the smaller half of this change.

The Messages API rejects sampling parameters (`temperature`, `top_p`, `top_k`) on every current Anthropic model. `synthesizeDegradedReply` asks for `temperature: 0`, so on any 5-series model the degraded-reply synthesis call would have failed with a 400 — and because that call is deliberately wrapped in a catch that falls through to the fixed apology string, it would have failed *silently*, reporting `agent.degrade.synthesis ok:false` on every degrade with nothing else to show for it. This was already reachable before the default moved: operators can register any model id, so anyone who ran `/model claude-opus-5` was already on this path.

`temperature` stays on `ChatParams` and stays honoured by the OpenAI-compatible adapter, where it is valid and useful (xAI, OpenRouter, local vLLM all accept it). `AnthropicProvider` now strips it and logs once per model, so a caller asking for determinism can see that Anthropic isn't granting it rather than assuming it landed. The degrade callsite keeps requesting `temperature: 0` — best-effort by design, honoured wherever the provider supports it.

The `thinking` / `budget_tokens` path is deleted rather than migrated. `budget_tokens` is also a 400 on the 5-series, but `ChatParams.thinking` had no callers, so this was a dead code path that would have failed the first time anything used it. The adapter now sends no `thinking` parameter at all, which leaves each model its own default — adaptive thinking on Sonnet 5 and the rest of the 5 series, unchanged behaviour on 4.6. Explicit depth control belongs in `output_config.effort`, the parameter that replaced per-model token budgets; nothing needs it yet, so it isn't added speculatively.

Turning thinking on by default then exposed two more dormant faults on the response side, both invisible while we never sent a `thinking` parameter. Recording the integration fixtures against the real API is what surfaced them, as a `400 messages.1.content.0.thinking: each thinking block must contain thinking` on the second iteration of the first tool-using turn.

The first is in the streaming adapter: a thinking block's signature arrives in its own `signature_delta` event just before `content_block_stop`, and the delta switch didn't handle that case. It read `signature` from `content_block_start`, where the field is empty. Every thinking block the adapter rebuilt therefore carried an empty signature.

The second is `clearOldThinking`, which blanked the thinking text of every assistant message except the most recent to save context tokens. Both faults are the same underlying mistake: the Messages API accepts thinking blocks passed back exactly as received — including ones whose text is empty — and rejects blocks that have been edited or reconstructed. Blanking is an edit; a re-derived empty signature is a reconstruction. `clearOldThinking` had in fact already caused one production failure on the other adapter, which `openai-compat.test.ts` still carries a regression test for: an assistant turn left with nothing but zeroed thinking serialises to `content: null` and 400s OpenAI-compatible backends.

So the loop now forwards history verbatim and `clearOldThinking` is gone. Its token-saving rationale no longer holds regardless: `display` defaults to `omitted` on the 5 series, so the text it was clearing is already empty. Dropping the blocks instead of blanking them is not the fix either — removing them can trigger ordering and signature errors. If thinking ever creates real context pressure, the mechanism is server-side context editing (`clear_thinking_20251015`), not client-side rewriting.

Response-side translation of thinking blocks is otherwise unchanged — the streaming accumulator and history mapping still carry them both ways.

`skill-authoring.integration.test.ts` is disabled, and not because of anything above. Re-recording it revealed that the skill it authors has never been able to run: the prompt asks for `urllib.request` with no declared dependencies, which lands the skill in tier 1, where Pyodide has no raw sockets and no HTTP path at all — the fetch shim `design/skills.md` describes was never wired. The recorded turns from May show the model discovering exactly that at runtime and falling back to `web_answer`, so the closing price assertion has always been satisfied by a live unmocked Perplexity call rather than by the skill under test. That fallback returned something the model judged stale this time, and it declined to state a number. Everything before that point still works — authored, pushed, merged, registered, invoked as a tool on the next turn — so the suite is disabled rather than deleted, pending a real tier-1 network path. Both halves are tracked in `todo.md`.
