`/health` reports work that stops silently. A liveness registry evaluates every check every 15 s, and `/health`'s `status` is `warn` while any check warns, still at HTTP 200 so a status-code probe restarts cogmo only once it stops answering. The checks themselves (`telegram:polling` and `channels:adapter`) appear only for a request with a valid web UI session; a session lookup that fails or takes over 2 s gets the public body. Both bodies are sent with `Cache-Control: no-store`. The same verdicts export as the `cogmo.check.status` gauge, a state set with exactly the attributes `check`, `component_id` and `status`, and each change of verdict logs one `liveness check warn` or `liveness check pass` line.

`telegram:polling` warns `failed` (a 401 or another rejection), `wedged` (a handler holding an update 5 min), `flapping` (a second 409 in a row), `retrying` (90 s of errors grammY retries) or `stale` (90 s with no batch or finished update). A channel row whose type the build has no adapter for warns `unsupported`.

An update without a safe-integer `update_id`, which only a misbehaving custom `apiRoot` sends, credits no progress and never reaches the offset `stop()` confirms, so a `NaN` offset can't make the next start redeliver handled updates. A Telegram channel's setup registers its bot token with the logger, which masks it by value in every line, raw or percent-encoded, so a custom `apiRoot` echoing the bare token in an error leaks nothing into a log line; the logger's token shape also matches a percent-encoded slash (`%2Fbot`).
