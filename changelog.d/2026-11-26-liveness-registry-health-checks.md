`/health` reports work that stops silently. A liveness registry (`src/liveness/`) evaluates every check every 15 s, and `/health`'s `status` is `warn` while any check warns, still at HTTP 200 so a status-code probe restarts cogmo only once it stops answering. The checks themselves (`checks`, keyed `telegram:polling` and `channels:adapter`, each with a `reason`, a fixed-text `output` and the seconds since its last progress) appear only for a request with a valid web UI session. A session lookup that fails or takes over 2 s gets the public body. Both bodies are sent with `Cache-Control: no-store`. The same verdicts export as the `cogmo.check.status` gauge, a state set with exactly the attributes `check`, `component_id` and `status`, and each change of verdict logs one `liveness check warn` or `liveness check pass` line.

The Telegram adapter tracks its receive loop beside the polling supervisor: an API transformer sees every `getUpdates` outcome, including the ones grammY retries, and the update-tracking middleware records the update in hand. `telegram:polling` warns `failed` (a 401 or another rejection), `wedged` (a handler holding an update 5 min), `flapping` (a second 409 in a row), `retrying` (90 s of errors grammY retries) or `stale` (90 s with no batch or finished update). A channel row whose type the build has no adapter for warns `unsupported`. `Adapter` and `StreamingAdapter` both require `liveness(): ChannelLiveness | null`, and the direct and web adapters return `null`.

An update without a safe-integer `update_id`, which only a misbehaving custom `apiRoot` sends, credits no progress and never reaches the offset `stop()` confirms, so a `NaN` offset can't make the next start redeliver handled updates. The adapter masks its bot token, raw and percent-encoded, in every line it writes that carries a Bot API error, and the logger's token shape also matches a percent-encoded slash (`%2Fbot`).
