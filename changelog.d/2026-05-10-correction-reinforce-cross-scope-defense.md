Code-level defense against cross-scope correction reinforcement, the follow-up to PR #197 ("Observer channel-scoped extraction"). PR #197 left the cross-scope safety net at the prompt: the extraction prompt instructs the LLM to emit a wording-match against a different-scope rule as `new` with the right `channelType`, and the `reinforce` schema variant deliberately omits `channelType` so it can't be used to relabel an existing row. The gap was that nothing in code rejected an out-of-scope `reinforce` if the LLM ignored the instruction — `applyCorrection` would happily increment a global rule's `observation_count` (and possibly graduate it) from a Telegram-only conversation, or vice versa.

`extractCorrections` now validates the matched rule's stored `channelType` against the conversation's active channel set before calling `applyCorrection`. The matched rule was already loaded for the prompt's dedup context (`existingRules` from `getCorrections`), so the check costs nothing at the DB layer — a `find` on an in-memory array. Global rules (`channelType === null`) always pass; channel-scoped rules pass only when their `channelType` is in the active set; out-of-scope and hallucinated-id matches both skip with a structured warning that mirrors `coerceChannelType`'s shape so audit grepping stays uniform. The prompt remains the steering signal — this is the safety net for when the LLM ignores it.

`ExtractionResult` gains a `crossScopeReinforcementsSkipped: number` field. The Observer's audit log already returns the full `ExtractionResult` under `corrections` in its per-fire status payload, so the new counter surfaces there for free — no observer.ts change needed. The comment block above `applyCorrection` now describes the present-tense gate (validation before upsert, the prompt-vs-code division of labour, the global-rule fast path, the hallucinated-id case) rather than the prior gap.

Test additions in `src/agent/evolution/extract-corrections.test.ts`: four new cases — global-rule reinforce passes regardless of active channels, in-scope channel-rule reinforce passes, out-of-scope channel-rule reinforce skips and counts, hallucinated `matchedExistingRuleId` skips and counts. Existing reinforce-shaped tests (`reinforces existing correction`, `tracks promotions from upsertCorrection`, `handles mixed corrections in one extraction`) now seed `getCorrections` with the matched rule so the new gate doesn't drop them. 119 evolution-module tests pass; typecheck and lint clean.
