Agents-as-tools: the orchestrator can now delegate a subtask to a **sub-agent** — a specialist model exposed as a `subagent__<name>` tool. This is the answer to "this model is great at a feature but can't run tools": the orchestrator holds the tools, the specialist runs tool-free and returns text, and the orchestrator acts on it. A sub-agent can target any model routable via `model_providers`, including a different provider than the main turn.

New `sub_agents` table — a per-user catalog that's a thin binding over a routable model: `name` (→ the tool name), `description` (the routing signal the orchestrator reads to decide when to delegate), `system_prompt` (nullable — null is a pure model-as-tool whose per-call task carries all instruction; set is a persona reused across calls), and `model` (validated to exist in `model_providers`, but not `user_selectable`-gated, like `profiles.summarization_model`).

No profile↔sub-agent join table: availability is per-profile through the existing `profiles.tool_set` globs, the same mechanism that gates built-ins, skills, and MCP tools. A profile opts in by listing `subagent__<name>` (or `subagent__*`); definitions stay global and reusable. The `subagent__` namespace mirrors `mcp__` so a sub-agent tool can't collide with a built-in.

v0 runtime is text-in/text-out. `buildSubAgentTools` turns each row into a tool whose handler resolves the model and runs a single `provider.chat({ system, messages })` with **no tools** passed — the specialist physically cannot tool-call. The handler is `durable` (a `handle-message` retry replays the cached result instead of re-billing the call), `parallelSafe`, `sideEffectful: false` (so a turn that only delegates doesn't read as progress to the loop-pathology gate), and capped at 3 invocations per turn. `handle-message` reloads the rows each turn, so CLI changes take effect on the next turn without a restart. This keeps the orchestrator-holds-secrets invariant trivially — the specialist never receives a `Service` or a key.

Managed via a new `cogmo subagent add/list/remove` CLI, sharing a `create-sub-agent` use case. Nested-loop sub-agents (their own toolset) and richer CRUD surfaces (wizard step, web UI, Telegram `/subagent`) are deferred.
