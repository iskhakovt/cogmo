Tool handlers resolve to `Result<string, ToolRejection>`, so a rejected call reaches the model, delivery and the stuck-loop detector as an `is_error` result.

- **Contract.** A handler returns `ok(content)` or `reject(message)`. The loop answers a rejection with `{ content: "Error: <message>", isError: true }`. A throw out of a handler is a bug: it still becomes an `is_error` result, and is logged at error level.
- **Durable tools.** A `tool-iter<N>-<P>` step memoizes `{ ok: true, content } | { ok: false, message }`, parsed with Zod on every invocation, so a rejection replays like any result. A run in flight may hold a bare-string memo; it reads as a success.
- **Fixed.** `generate_image` and the scheduling and web tools returned their rejections as plain `"Error: …"` text. The Telegram stream handle tried to parse a rejected image as a payload (logging a misleading shape warning), and Class D counted a rejected side-effectful call as progress, so repeated identical rejections never tripped the stuck-loop.
- **Converted to rejections:** image pre-flight checks and every `ImageFailure`; scheduling, pipeline, core-memory, coding, skill and MCP refusals (an `isError` result, InvalidParams, MethodNotFound, a request timeout); file-tool mistakes (file not found, `old_string` missing or unchanged, a file changed since it was read); web tools unconfigured or refused upstream; `get_current_time` with an unknown timezone; sub-agent config, empty and truncated output. Domain code no longer imports Inngest's `NonRetriableError`.
- **Rules.** `.claude/rules/code-style.md` spells out where a throw is still right: a framework's channel (an Inngest step retry, p-retry's `AbortError`, oRPC's `fail`, a provider stream), fatal boot checks and invariant violations.
