Telegram streaming survives a failed write. One rejected edit, usually an unretried 429, poisoned the stream handle: every later edit, `finish` and `abort` rethrew without calling Telegram, the handle never left the adapter, and the Inngest retry reopened it. The handle is now a pure state machine (`stream-state.ts`) that classifies failures as grammY's auto-retry plugin does: it waits out a 429's `retry_after` and retries a 5xx or network error with backoff from 1 s, under one cap (no wait over 30 s, five failures in a row, and a closing stream done within 60 s). An HTML parse error falls back to plain text, and when the message being edited is gone the stream carries on in a new one. Anything else fails the handle cleanly: it settles, stops its typing heartbeat and leaves the adapter, so a retry streams into a fresh message without resending the run's photos. A reply whose stream fails at finish goes out again through a durable `redeliver-unstreamed` step, so an append-only chat is never left without it. The delivery router fans out with `Promise.allSettled`, so one failing chat no longer keeps a web tab from its `turn-abort`, and a failed abort no longer replaces the turn's own error.
