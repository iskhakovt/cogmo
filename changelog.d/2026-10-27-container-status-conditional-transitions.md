**Container rows move through an explicit state machine, one conditional transition at a time.** `SandboxStore.transitionContainerStatus(tx, { id, from, to, at })` replaces the unconditional `updateContainerStatus`: a single `UPDATE … WHERE id = $1 AND status = <from>` returning `{ kind: "transitioned" } | { kind: "stale"; status }`, the shape of `DrizzleCodingStore.transitionTaskStatus`, with the legal transitions encoded in the `ContainerTransition` type. `at` stamps `started_at` on the way into `running` and `exited_at` into a terminal state; a row already `exited` keeps its `exited_at` when it is reaped. Two use cases own the terminal transitions — `reapContainer` (kill + remove the daemon object, then move to `reaped`) and `markContainerExited` — and every writer goes through them: the supervisor's `create` start-failure and `deleteByTaskId` cascade, the boot-time `reconcileCrashedInstances`, and the reaper's TTL, orphan and stale passes. A `stale` result means a cascade or an overlapping tick finished the row first; it is logged at debug with the reap reason (`ttl_expired`, `cascade`, `dead_instance`, `crash_reconcile`, `start_failed`), not treated as an error, and not counted by the DB-driven passes, so the stale pass no longer rewrites a `reaped` row as `exited` and a racing cascade no longer overwrites the reaper's `exited_at`. A start failure now reaps the container (`starting → reaped`) rather than marking a removed container `exited`.

`create` also handles the daemon succeeding where the row insert fails: the container is force-removed and the proxy scope released before the error propagates, instead of leaving the orphan pass to find it.

`design/sandbox.md` gains a `[proposed]` Container state machine section — unit, states, transition table, failure-mode table — and the Lifecycle section describes the create and teardown flow as implemented. A `reaped_reason` column is the planned datum for the reason; it is a schema change for a follow-up. Writing the failure-mode table surfaced that proxy-created child containers get no row and so meet the orphan pass's "no row ⇒ orphan" rule; that is tracked in `todo.md`.
