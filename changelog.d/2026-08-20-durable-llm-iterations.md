**Durable LLM iterations — the agent loop no longer pays for every step boundary.** A field report (2026-08-19) showed a clean 7-tool turn invoking the model five separate times: Inngest re-invokes the whole function at *every step boundary on success*, and the streaming LLM call lived in the bare function body, so each durable tool call charged a fresh full model round-trip — the user watched five differently-worded preambles stream into Telegram while Postgres recorded one turn. The same non-determinism upstream of the durable tool steps produced the rarer `Could not find step … timed out` failure (replay emits a different tool shape than the cached plan), which silently dropped inbound messages for the cooldown window.

The premise that forced the bare-body call — "you cannot stream out of `step.run`" — confused returning a stream from a step (impossible) with emitting to a transport from inside the body (normal, and suppressed on replay, which is exactly the desired behavior). Each streaming iteration now runs inside `step.run("llm-iter<N>")`: the body drains the stream (tokens reach the delivery layer live), runs the Class C classifier and non-streaming replay in-step so their verdicts cache as data instead of escaping as blind-retried throws, and returns a JSON outcome carrying the content plus an `emitted` ledger. Replays reproduce the iteration bit-for-bit — no provider call, no re-emission, identical downstream step graph, deterministic repair budgets. The degraded off-ramp (synthesis LLM call + retract/apology pushes) moved into a `degraded-reply` step, auto-recall into an `auto-recall` step, the compaction status banner into the `summarize-prefix` body, and the orchestrator's retraction now reads the loop-derived `streamed` ledger (a live-emission ledger is empty on replay). Cached durable tools also stop re-emitting their `tool_result` events, closing the duplicate-photo-card path.

The same boundary-counting flipped the tool durability policy from "wrap sparingly" to "side-effectful or billable ⇒ durable": a non-durable handler re-executes once per remaining boundary, so `schedule_task` inserted duplicate reminders, `delegate_coding` could spawn duplicate tasks, and `web_search`/`fetch_url`/`memory_recall` re-billed per boundary. Flipped: `memory_recall`, `memory_retain`, `web_search`, `fetch_url`, `write_file`, `edit_file`, `core_memory_update`, `schedule_task`, `remove_task`, `activate_pipeline`, `delegate_coding`, `register_skill`, and every per-skill dynamic tool (arbitrary side-effecting Python — the flip also gives the agent-loop invocation path exactly-once semantics that the skills idempotency-key design had deferred). Cheap idempotent reads (`read_file`, `list_*`) stay bare. Obsolete machinery from the old world was removed where it was genuinely dead (`ContextManagerDeps.onStatus` — the status banner now lives inside the `summarize-prefix` step body) and kept where it still guards the mid-step-crash path (`#activeStreams` runId dedup, `#sentImages` media dedup, position-keyed `tool-iter<N>-<P>` step ids).

Why it was missed, and the guard against recurrence: `design/crash-recovery.md` reasoned entirely about *retries* — every cost sentence was conditioned on failure, so nobody multiplied replay cost by the durable-tool count of a normal turn. The doc is rewritten around the per-boundary model (checkpointing is an optimization with fallbacks — parallel steps, step retries, connect `maxRuntime` 300s — not the contract), and a new `.claude/rules/inngest.md` makes boundary-counting, in-body emission, conditional-step determinism, and the self-invalidating-status-guard trap (found in the coding orchestrators during the same audit — filed as a `p1`) standing instructions. New regression coverage: loop-level cached-iteration tests, wire-level `@inngest/test` cases for `llm-iter1`/`degraded-reply`/`auto-recall`, and the long-owed `#activeStreams` retry-dedup test on the Telegram adapter.
